# 自动化安全评估系统后端开发规范

## 1. 文档说明

### 1.1 目的

本文档定义自动化安全评估系统（ASA System）MVP 后端工程的技术选型、分层架构、目录结构、编码规则、接口实现、任务调度、数据一致性、安全、日志、测试、接口文档和交付门禁。API、Worker、Event Relay、Executor 及共享后端代码的开发和评审必须遵循本规范。

### 1.2 设计依据

- `docs/1_PRD/自动化安全评估系统-PRD.md`
- `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md`
- `docs/4_开发规范/API接口文档.md`
- `docs/4_开发规范/数据库/数据库设计.md`
- `docs/4_开发规范/数据库/字段规范.md`
- `docs/4_开发规范/数据库/初始化sql.md`

发生冲突时，业务范围和验收标准以 PRD 为准，技术路线和系统边界以概要设计总纲为准，对外协议以 API 接口文档为准，表结构和约束以数据库设计及字段规范为准。实现不得私自新增状态值、接口字段或数据库语义。

### 1.3 适用范围

本规范适用于：

- `apps/api/`：FastAPI REST API 和 WebSocket 服务。
- `apps/worker/`：Celery Worker、阶段调度、AI 角色、报告、清理和 Event Relay 入口。
- `apps/executor/`：隔离执行网关。
- `packages/backend-core/`：领域、应用、持久化及公共后端能力。
- `packages/contracts/`：OpenAPI、实时事件和内部服务协议。
- `migrations/`：Alembic 数据库迁移。
- `tests/`：单元、接口、契约、集成和端到端测试。

### 1.4 规范级别

- “必须”表示合并前不可违反。
- “禁止”表示不得采用。
- “应”表示默认执行，偏离时必须说明原因和风险。
- “可”表示按实际场景选择。

## 2. 核心原则

### 2.1 数据库是事实源

项目、运行实例、阶段、角色任务、漏洞、攻击路径、报告、日志、资源和配置状态以 PostgreSQL 持久化记录为准。Redis、Celery、WebSocket、LangGraph 和进程内缓存均不得作为业务状态的唯一来源。

状态变化必须先提交数据库，再向外发布事件。事件发布失败不得回滚已经提交的业务状态，必须通过 Outbox 重试恢复。

### 2.2 控制面与执行面分离

- API 只负责认证、权限、校验、查询和任务受理。
- Worker 负责异步调度、AI 调用、报告生成和清理。
- Executor 负责容器生命周期、文件工具和受控命令。
- API 和 Worker 禁止直接访问 Docker Socket。
- Executor 禁止直接访问业务数据库和 Redis。
- 浏览器不得访问 Worker、Executor、PostgreSQL、Redis 或 Docker Engine。

### 2.3 领域规则集中

项目状态机、阶段推进、权限、幂等、漏洞去重、攻击路径约束和报告状态等规则必须集中在领域或应用层。Router、Celery Task、Repository 和 ORM Model 不得各自实现一套状态判断。

### 2.4 事务边界明确

- 单个业务状态变化及对应 Outbox 事件在同一数据库事务内提交。
- 外部 HTTP、Docker、文件、模型和消息队列调用不得包在数据库长事务内。
- 跨数据库与外部资源的流程使用可恢复的分步操作，不伪装成分布式事务。
- 所有可重试步骤必须幂等。

### 2.5 最小权限与不可信输入

HTTP 输入、WebSocket 参数、模型输出、源码路径、Git 地址、文件内容、命令参数和外部服务响应都视为不可信。必须在进入业务边界时校验，在进入日志、事件、模型上下文和报告前再次过滤敏感信息。

### 2.6 简单优先

- MVP 使用模块化单体 API 和独立 Worker，不提前拆分大量微服务。
- 不建立通用工作流平台、通用规则引擎或自研 ORM。
- 同类逻辑稳定重复后再抽取公共能力。
- 不为隐藏简单调用创建无业务意义的多层包装。
- 不以全局单例、隐式上下文和动态导入替代明确依赖。

## 3. 技术栈与工程工具

### 3.1 运行技术栈

| 分类 | 技术 | 约束 |
| --- | --- | --- |
| 语言 | Python 3.12 | 所有服务使用同一小版本 |
| Web 框架 | FastAPI | REST、WebSocket、依赖注入和 OpenAPI |
| 数据模型 | Pydantic 2 | 请求、响应、配置、任务和事件校验 |
| ORM | SQLAlchemy 2 | 使用 typed declarative mapping |
| 数据迁移 | Alembic | 禁止应用启动时隐式改表 |
| 异步任务 | Celery 5 | 阶段执行、AI 调用、报告、清理和重试 |
| AI 编排 | LangGraph | 只编排单个阶段内的角色执行图 |
| 模型接入 | OpenAI 兼容适配层 | 统一 LLM 与 Embedding 调用的超时、重试、输出校验和 token 统计 |
| 向量存储 | pgvector（PostgreSQL 扩展） | 保存安全知识 Embedding 向量并支持 IVFFlat/HNSW ANN 检索 |

| 密码 | Argon2id | 密码哈希与验证 |
| 数据库 | PostgreSQL 15 及以上 | 保存全部权威业务数据 |

| 测试 | Pytest、HTTPX、Testcontainers | 单元、接口和中间件集成测试 |

### 3.2 质量工具

- Ruff 负责格式化、导入排序和静态规则。
- mypy 负责严格类型检查。
- Pytest 负责测试执行。
- pytest-cov 负责覆盖率统计。
- Alembic 负责迁移升级、降级策略记录和 schema 版本。
- OpenAPI 生成脚本负责契约差异检查。

不得同时引入 Black、isort 与 Ruff 执行重复格式化，也不得同时采用多套互相冲突的类型检查规则。

### 3.3 依赖管理

- 仓库只保留一个根 `pyproject.toml` 和一种锁文件。
- API、Worker、Executor 和开发工具按 dependency group 管理，避免每个应用维护漂移的版本。
- 生产依赖必须锁定可重现版本，开发、CI 和镜像构建使用同一锁文件。
- 新增依赖前必须检查许可证、维护状态、安全公告、传递依赖和是否与现有能力重复。
- 禁止依赖个人本地路径、未固定 Git 分支和临时压缩包。
- 依赖升级必须说明 API 行为、数据库驱动、Celery 协议、模型输出和镜像体积影响。

### 4.2 API 目录

```text
apps/api/
└── src/
    └── asa_api/
        ├── main.py
        ├── bootstrap.py
```

- `agents/` 保存角色配置、上下文裁剪、工具权限、RAG 检索适配和 LangGraph 适配。

### 4.6 依赖方向

允许的依赖方向为：

```text
interface adapters → application → domain
infrastructure → application ports and domain
composition root → all concrete implementations
```

- `domain` 不得依赖 FastAPI、Pydantic、SQLAlchemy、Celery、Redis、Docker 或具体模型供应商。
- `application` 不得依赖 Router、ORM Model、Celery Task 和 Docker SDK。
- `infrastructure` 实现应用层 Port，不决定状态流转。
- `apps/*` 只作为入口、协议适配和依赖组装层。
- 领域对象不得直接序列化为 HTTP 响应。
- Repository 不得返回 Pydantic HTTP Schema。
- 模块间只能通过公开接口依赖，禁止跨目录导入内部实现。

## 5. 命名与编码风格

### 5.1 命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 模块、函数、变量 | `snake_case` | `start_project` |
| 类、异常、Schema | PascalCase | `ProjectStatusConflict` |
| 常量 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` |
| 私有成员 | 单下划线前缀 | `_load_project` |
| 数据库表和字段 | `snake_case` | `runtime_stages` |
| API 业务码 | UPPER_SNAKE_CASE | `PROJECT_START_ACCEPTED` |
| Celery Task 名称 | 点分层级 | `asa.projects.start` |
| Prometheus 指标 | `asa_` 前缀 | `asa_api_requests_total` |

- 布尔值使用 `is_`、`has_`、`can_` 或 `should_`。
- 时间点使用 `*_at`，时长使用明确单位后缀，如 `timeout_seconds`。
- 集合使用复数名，单个实体使用单数名。
- 禁止使用 `data`、`info`、`manager`、`handler`、`helper` 等无法表达职责的泛化名称。
- `Service`、`Repository`、`Gateway` 和 `Policy` 后缀必须与实际职责一致。

### 5.2 函数与类

- 函数只完成一个可描述目的。
- Router、Task 和异常处理器保持薄层，不承载领域分支。
- 类优先组合，不使用深层继承。
- 无状态转换使用纯函数，不为纯函数创建单例类。
- 参数超过合理数量时使用明确的 Command、Query 或值对象，不传递无类型字典。
- 公共函数和类必须有完整类型标注。
- 返回值可能为空时显式使用 `None`，不得用空字符串、空 UUID 或魔法值代替。

### 5.3 类型与枚举

- 领域状态使用 `StrEnum`，值与数据库 CHECK 和 API 契约一致。
- 不建立跨领域“通用状态枚举”。
- UUID 使用 `uuid.UUID`，时间使用带时区的 `datetime`。
- 金额、比例和精确计量使用 `Decimal`；CPU 百分比不得在领域层随意转为浮点。
- 外部 JSON 使用 Pydantic Model 校验后再进入应用层。
- 禁止以 `dict[str, Any]` 在多个层之间传递业务数据。
- `cast`、`# type: ignore` 和不安全断言必须说明第三方类型缺陷，不能用于掩盖设计错误。

### 5.4 异步与阻塞

- 同一调用链必须明确是同步还是异步，不在深层函数中隐式创建事件循环。
- Celery Task 和共享数据库访问采用可预测的同步边界。
- FastAPI 同步 REST Handler 由线程池执行，不得在 `async def` 中直接调用同步数据库、文件或 Docker 客户端。
- WebSocket 和 Redis Stream 使用异步 I/O；需要调用同步查询时通过明确的线程边界执行。
- 禁止在请求和任务代码中使用无上限线程池或进程池。

### 5.5 注释与 Docstring

- 注释解释业务约束、取舍和失败恢复方式，不复述代码。
- 公共应用服务、Port、协议模型和安全策略必须编写 Docstring。
- Router 的 `summary`、`description`、`responses` 和 `operation_id` 必须完整。
- 待办使用可追踪标识，不提交无负责人和无条件的长期 `TODO`。

## 6. 配置与应用启动

### 6.1 配置模型

- 配置使用 Pydantic 2 校验，按 API、Worker、Executor 和共享基础设施拆分。
- 环境变量名称使用统一 `ASA_` 前缀。
- 配置项必须注明类型、默认策略和是否敏感。
- 未经 PRD 或部署评审确认的并发数、保留天数、模型名称和资源配额不得写死默认值。
- 启动时一次性校验必要配置，错误信息指出缺失项但不得回显敏感值。
- 业务代码只依赖配置对象，不在模块内部反复读取环境变量。

### 6.2 敏感配置

- 数据库密码、Redis 密码、模型密钥、Git 凭证、证书和内部服务凭证只从受控密钥来源注入。
- 敏感字段的 `repr`、日志和错误输出必须脱敏。
- 禁止把 `.env`、密钥和证书提交到仓库。
- 测试使用虚假凭证，不复用开发或生产值。

### 6.3 生命周期

应用启动顺序应为：

1. 加载并校验配置。
2. 初始化结构化日志和指标。
3. 创建数据库、Redis、外部客户端和连接池。
4. 注册 Router、Middleware 和异常处理器。
5. 执行依赖就绪检查。

应用关闭时停止接收新请求，等待受控中的请求，关闭 WebSocket、客户端和连接池。API 和 Worker 启动时不得自动执行 Alembic migration。

### 6.4 健康检查

- 存活检查只判断进程事件循环或主线程是否正常。
- 就绪检查验证 PostgreSQL、Redis 及当前进程必需依赖。
- API 就绪检查不得验证 Docker Socket，因为 API 不应访问 Docker。
- Executor 单独检查 Docker Engine 和策略加载状态。
- 健康接口不得返回连接串、版本细节、主机路径和密钥。

## 7. REST API 实现规范

### 7.1 路径与版本

- 对外路径统一使用 `/api/v1`。
- 资源使用复数名词和 kebab-case，不在 URL 中使用动词表达普通 CRUD。
- 启动和停止等领域动作使用明确子资源动作路径，保持现有接口文档定义。
- 不为内部 Worker 和 Executor 操作复用浏览器 API。
- 破坏性协议变更必须使用新版本前缀，不在 `/api/v1` 原地改变含义。

### 7.2 Router 职责

Router 只执行：

1. 解析路径、查询、请求头和请求体。
2. 注入当前用户和应用服务。
3. 构造 Command 或 Query。
4. 调用一个应用用例。
5. 将结果转换为统一响应。

Router 禁止直接：

- 查询或提交 SQLAlchemy Session。
- 调用 Redis、Celery、Docker、文件系统或模型。
- 编写项目状态流转和权限过滤。
- 捕获所有异常后返回 `200`。
- 返回 ORM Model 或内部异常文本。

### 7.3 Pydantic Schema

- 请求、响应、任务和事件使用不同 Schema，不复用一个万能模型。
- 请求模型默认拒绝未知字段，使用 `extra="forbid"`。
- 字符串使用 `min_length`、`max_length` 和规范化校验。
- 枚举使用闭集类型，不接受任意字符串后再静默回退。
- 输入 Schema 不允许客户端提供 `id`、状态、创建者和审计字段。
- 输出 Schema 按页面需要裁剪，不返回密码哈希、凭证、内部逻辑路径和无关大文本。
- `from_attributes=True` 只用于明确的输出模型。
- 自定义校验器只做字段和结构校验，不执行数据库或网络 I/O。

### 7.4 统一响应

除文件下载和 WebSocket 外，所有成功和失败响应使用：

```python
from typing import Generic, TypeVar
from uuid import UUID

from pydantic import BaseModel

DataT = TypeVar("DataT")


class ApiResponse(BaseModel, Generic[DataT]):
    code: str
    message: str
    data: DataT
    request_id: UUID
```

- `code` 是稳定业务标识，不使用中文和动态字符串。
- `message` 面向用户，不包含堆栈和内部组件信息。
- `request_id` 同时写入响应头 `X-Request-ID`。
- 无数据时 `data` 返回 `null`，不省略字段。
- HTTP 状态码必须表达协议结果，不把所有业务错误包装为 `200 OK`。

### 7.5 分页和游标

- 普通列表使用 `page`、`page_size`，最大页大小为接口文档规定值。
- 日志、消息和资源使用稳定游标，不使用 `OFFSET` 扫描不断增长的大表。
- 游标必须绑定查询条件或采用不可篡改编码，防止跨项目复用。
- 排序必须包含稳定次级键，例如 `(created_at, id)`。
- 所有列表先应用用户和项目权限过滤，再分页和计数。
- 禁止无上限查询日志、资源、消息、证据和报告历史。

### 7.6 请求标识与幂等

- Middleware 接受合法 `X-Request-ID` 或生成 UUID。
- `request_id` 通过显式上下文传入日志、审计、任务和外部调用。
- 启动、停止和删除必须校验 `Idempotency-Key` 长度和格式。
- 同一用户、项目、操作和 Key 的重试返回首次受理结果。
- 同一 Key 用于不同项目、操作或请求内容时返回 `409 IDEMPOTENCY_KEY_REUSED`。
- 幂等记录必须持久化，不得只放在 Redis 或进程内缓存。
- 幂等判断和任务记录创建必须位于同一事务。

### 7.7 HTTP 状态码

必须遵循现有接口契约：

| 状态码 | 用途 |
| ---: | --- |
| `200` | 查询、登录、退出和同步更新成功 |
| `201` | 初始化和项目创建成功 |
| `202` | 启动、停止和删除已受理 |
| `400` | JSON 或协议格式无法解析 |
| `401` | 未认证或会话过期 |
| `403` | 无角色、项目或 CSRF 权限 |
| `404` | 资源不存在 |
| `409` | 状态、容量、幂等或版本冲突 |
| `422` | 字段、路径和查询参数校验失败 |
| `429` | 触发限流 |
| `500` | 未预期服务端错误 |
| `503` | 必需依赖不可用 |

### 7.8 文件响应

- 报告下载前校验会话、项目权限、报告状态和文件完整性。
- 文件路径通过 `ArtifactStorage` 逻辑键解析，禁止使用用户输入拼接宿主机路径。
- 下载文件名执行字符白名单处理。
- 设置正确的 `Content-Type`、`Content-Disposition`、`Content-Length` 和安全缓存头。
- 使用强 ETag 时仍必须先完成权限校验。
- 文件缺失与摘要不匹配使用不同业务错误码并记录审计。

## 8. 认证、授权与审计

### 8.1 密码和初始化

- 密码只保存 Argon2id 哈希。
- 初始化必须先获取事务级全局 advisory lock，再在同一数据库事务中确认系统尚未初始化并创建管理员，防止并发创建多个初始管理员。
- 用户名在应用层规范化为小写并由数据库唯一约束兜底。
- 登录错误统一返回 `INVALID_CREDENTIALS`，不得泄露用户名是否存在。
- 密码、密码哈希和完整认证头不得写入日志、事件和审计元数据。

### 8.2 会话

- 登录成功按接口契约设置 `asa_session` 和 `asa_csrf` Cookie。
- `asa_session` 使用 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 会话值必须不可预测、可过期、可撤销，不在 Cookie 中暴露密码、角色和敏感项目数据。
- 退出必须使服务端会话失效，不能只清除浏览器 Cookie。
- 会话过期统一返回 `401 SESSION_EXPIRED`。
- 会话存储和撤销机制必须在认证详细设计中确定，不能由各进程自行实现。

### 8.3 CSRF

- 使用 Cookie 认证的 `POST`、`PUT`、`PATCH` 和 `DELETE` 必须校验 `X-CSRF-Token`。
- CSRF 比较使用恒定时间方法。
- Token 不得进入 URL、业务日志、审计、事件和错误响应。
- WebSocket 握手必须校验 Origin、会话和项目权限。

### 8.4 权限模型

- 普通用户默认只能访问本人创建的项目。
- 所有项目子资源查询同时包含 `project_id` 和当前用户权限条件。
- 禁止先按子资源 ID 查询再在应用层补做项目归属判断。
- 管理员只对系统配置拥有额外权限；管理员访问项目敏感资源仍遵循项目权限规则并记录审计。
- 权限检查集中在应用服务或 Repository 范围对象，不在每个 Router 手写。
- 资源不存在与无权限的响应策略必须一致，避免通过差异枚举其他用户资源。

### 8.5 审计

以下操作必须写入脱敏审计记录：

- 初始化。
- 登录成功、连续登录失败和会话失效。
- 越权访问。
- 项目创建、启动、停止和删除。
- 系统配置更新。
- 管理员访问敏感项目资源。
- 报告下载和文件完整性失败。

审计写入失败时，安全敏感写操作不得静默成功。审计元数据只使用白名单字段，不保存请求体、Cookie、密码、模型密钥和完整日志。

## 9. 领域模型与状态机

### 9.1 项目状态

权威状态只允许：

- `created`
- `running`
- `completed`
- `failed`
- `stopped`

允许的主流程为：

```text
created → running → completed
created → running → failed
created → running → stopped
created → failed
```

- 环境准备成功后才能进入 `running`。
- 源码接入或环境准备失败可由 `created` 进入 `failed`。
- 终态不得回到 `created`。
- MVP 不支持原地重跑。
- 同一项目同一时刻最多一个运行实例。
- 状态迁移由一个领域策略定义，禁止在多个服务重复维护转移表。

### 9.2 阶段状态

阶段固定为：

1. `environment_scan`
2. `code_analysis`
3. `vulnerability_verify`
4. `report_generate`
5. `done`

阶段和角色任务状态只允许 `idle`、`running`、`success`、`failed`。项目停止不增加阶段或任务的 `stopped` 状态；取消原因写入任务结果或错误摘要，项目最终进入 `stopped`。

### 9.3 状态迁移实现

状态迁移必须同时检查：

- 当前权威状态。
- 目标状态。
- 操作者权限或任务身份。
- 前置阶段结果。
- 取消标记。
- 并发运行和幂等记录。

持久化使用带期望旧状态的条件更新或行锁。受影响行数不为 `1` 时返回领域冲突，不执行后续副作用。

### 9.4 领域异常

领域层定义稳定异常，例如：

- `ProjectNotFound`
- `ProjectAccessDenied`
- `ProjectStatusConflict`
- `ProjectCapacityExceeded`
- `InvalidStageTransition`
- `VulnerabilityNotFound`
- `AttackPathNotFound`
- `ReportNotReady`

异常只携带安全上下文和业务标识，不携带 HTTP Response。API 异常映射器负责转换状态码和业务码，Worker 负责转换任务结果和重试策略。

## 10. 数据访问与事务

### 10.1 SQLAlchemy Model

- 使用 SQLAlchemy 2 typed declarative 和 `Mapped[T]`。
- Python 可空性与数据库 `NULL` 约束保持一致。
- 数据库默认值使用 `server_default`，不能只写 Python 默认值。
- 约束和索引名称与数据库设计一致。
- 所有时间为带时区 `datetime`。
- ORM Model 只描述持久化映射，不实现跨聚合状态机。
- 不在 Model 属性访问中触发隐式网络或大查询。

### 10.2 Repository

- Repository 按聚合或稳定查询能力设计，不按数据表机械创建。
- 接口定义在应用 Port，SQLAlchemy 实现在 Infrastructure。
- 写 Repository 接受领域对象或明确参数，不接受 HTTP Schema。
- 查询 Repository 返回领域对象或专用只读投影。
- 列表查询显式字段裁剪，避免加载大文本和不需要的关系。
- 关系加载策略必须消除 N+1，并通过查询测试验证。
- Repository 不提交事务。

### 10.3 Unit of Work

- 应用用例显式开启 Unit of Work。
- `commit` 只在用例成功路径执行。
- 异常时必须回滚并释放 Session。
- Repository 共享同一用例 Session。
- 不允许内部 Repository 自行提交，避免部分状态提前落库。
- 事务结束后再执行 Celery、模型、Executor 和文件等外部调用。

### 10.4 锁与并发

- 项目启动、停止、阶段推进、事件序号分配和配置切换使用明确锁策略。
- 锁顺序固定，避免跨模块反向加锁。
- 不在持有数据库锁期间等待外部服务。
- 短暂死锁允许有限重试，业务状态冲突不得自动重试。
- 计数、唯一约束和条件更新由数据库兜底，不采用“先查再写”作为唯一保护。

### 10.5 Outbox

业务状态和 `domain_events` 必须同事务写入：

```text
load and lock aggregate
→ validate transition
→ persist business changes
→ allocate project sequence
→ append domain event
→ commit
```

- `event_id` 全局唯一。
- `sequence` 在项目范围严格递增。
- 序号分配在项目级锁内完成，禁止无锁执行 `MAX(sequence) + 1`。
- Event Relay 使用 `FOR UPDATE SKIP LOCKED` 批量领取。
- 发布成功后标记 `published`。
- 发布失败记录脱敏错误、重试次数和下次时间。
- Redis 消费方按 `event_id` 去重。

### 10.6 数据库迁移

- 所有结构变化通过 Alembic，禁止手工修改生产 schema。
- Migration 文件只做结构和必要数据迁移，不导入应用服务。
- 高频表新增非空字段采用“可空列、分批回填、增加约束”的分阶段方式。
- 新索引必须提供对应查询和 `EXPLAIN` 验证。
- 破坏性迁移必须提供兼容部署顺序、备份和回退说明。
- PostgreSQL 原生 ENUM 禁止使用，状态值域使用 `varchar` 和命名 CHECK。
- 首个 Migration 与 `初始化sql.md` 必须保持同源。

## 11. 异步任务与调度

### 11.1 任务消息

Celery 消息只包含可序列化标识和协议版本，至少包括：

- `project_id`
- `stage_id`
- `worker_task_id`
- `request_id`
- `idempotency_key`
- `schema_version`

禁止传递 ORM Model、数据库 Session、密码、Cookie、完整源码、模型密钥和超大上下文。

### 11.2 Task 边界

Celery Task 只负责：

1. 校验任务消息。
2. 建立日志和链路上下文。
3. 检查幂等结果和取消标记。
4. 调用一个应用服务。
5. 根据结果确认、重试或失败。

Task 不直接拼装 SQL、不自行推进多个阶段、不吞掉异常，也不把任意异常都标记为可重试。

### 11.3 重试

可重试错误包括：

- 短暂数据库死锁。
- 临时网络失败。
- Redis 或 Executor 短暂不可用。
- 模型限流和明确可恢复的供应商错误。

不可自动重试错误包括：

- 参数非法。
- 权限拒绝。
- 路径越界。
- 命令策略拒绝。
- 状态冲突。
- 模型输出结构持续非法。
- 确定性业务失败。

重试使用有限次数的指数退避和随机抖动。每次尝试更新 `attempt_count`，保留最后一次脱敏错误。达到上限后由调度服务将当前任务、阶段和项目收敛到正确失败状态。

### 11.4 幂等与投递恢复

- Task 执行前检查 `worker_task_id` 和幂等键。
- 已成功任务重复投递时直接返回已有结果，不重复执行模型、容器和文件副作用。
- 状态为 `running` 的陈旧任务根据心跳、容器和超时规则进入诊断流程，不直接假定成功或失败。
- API 事务提交后投递 Celery；投递失败必须保留可识别的待执行记录。
- 后台恢复流程扫描已受理但未开始的任务并按原幂等键重新投递。
- Worker 只在结果和状态持久化后确认消息完成。

### 11.5 阶段调度

- 阶段严格串行。
- 只有前一阶段为 `success` 才启动后一阶段。
- 阶段内仅对无依赖角色任务进行受控并行。
- 关键角色失败后不再创建后续任务。
- LangGraph 不得直接更新项目最终状态或推进跨阶段状态机。
- 项目并发数以生效系统配置和数据库权威状态计算，达到上限返回 `409 PROJECT_CAPACITY_EXCEEDED`，MVP 不建立无限等待队列。

### 11.6 停止

- 停止接口只允许 `running` 项目。
- API 原子写入 `stop_requested_at` 和取消信号所需记录。
- Worker 在角色调用前后、工具循环和阶段切换点检查取消。
- Executor 先发送终止信号，宽限期后强制终止项目容器内进程。
- 停止后不创建新任务和后续阶段。
- 已持久化漏洞、日志、资源、消息和报告草稿继续保留。
- Celery 撤销消息不能作为唯一取消机制。

## 12. AI 角色与模型调用

### 12.1 角色边界

六类角色固定为：

- `general`
- `environment_inspector`
- `code_analyst`
- `vulnerability_verifier`
- `report_editor`
- `operations_assistant`

每次角色调用都创建独立 `worker_tasks` 记录。角色只能获得所属阶段允许的工具，不能直接操作数据库、宿主机路径、Redis 和 Docker Socket。

### 12.2 模型适配层

- 业务代码只依赖统一模型 Port，不直接调用供应商 SDK。
- 适配层统一处理模型标识、超时、限流、重试、token 统计和错误映射。
- 供应商响应先转换为内部结果，再进入领域逻辑。
- 不在代码中写死供应商、模型名称、API 地址和 token 预算。
- 模型请求和响应日志只保存脱敏摘要、耗时、token 和错误类别，不保存完整源码与密钥。

### 12.3 上下文与输出

- 上下文按项目、阶段和角色最小化裁剪。
- 文件、搜索和命令输出设置字符、条数和 token 上限。
- 进入模型前过滤凭证、Cookie、密钥、环境变量和无关源码。
- 模型输出必须通过 Pydantic Schema 校验。
- 非法输出只在明确可恢复时有限重试。
- 模型自由文本不能直接变成 Shell 命令、路径或数据库更新。
- 漏洞风险、路径、行号和证据写入前执行业务校验和项目范围校验。

### 12.4 漏洞去重

- 候选漏洞使用项目、规则、规范化路径、位置和证据指纹去重。
- 指纹算法集中实现并有固定测试向量。
- 数据库唯一约束作为并发兜底。
- 唯一冲突时读取已有记录并安全合并，不把正常并发当作系统错误。
- 验证状态只允许 `pending`、`verified`、`rejected`。

### 12.5 RAG 知识检索

#### 12.5.1 知识库查询工具

`code_analyst` 和 `vulnerability_verifier` 角色默认启用知识库查询工具。该工具是角色唯一允许的数据库相关操作，但角色不直接访问数据库——工具由 Worker 端的安全检索服务实现，角色只看到结构化的检索结果。

工具定义：

```text
Tool: search_security_knowledge
  输入：自然语言查询文本
  输出：top-k 相关安全知识条目（标题、内容摘要、来源子库、相似度分数）
  约束：
    - 检索范围由 Worker 按当前项目的技术栈和阶段自动附加过滤条件
    - 角色不能绕过过滤条件进行全库任意查询
    - 每次调用最多返回配置上限条数
```

#### 12.5.2 Embedding 适配层

Embedding 调用复用 OpenAI 兼容适配层，与 LLM 共享认证基础设施，但通过独立的 Port 接口隔离：

```text
EmbeddingPort (application/ports/)
  ├── embed(texts: list[str]) → list[list[float]]
  ├── embed_query(text: str) → list[float]
  ├── dimension() → int
  └── health_check() → bool
```

约束：
- 业务代码只依赖 `EmbeddingPort`，不直接调用供应商 SDK。
- 向量维度在启动时自动检测，与 `knowledge_entries.embedding` 字段维度进行一致性校验。
- Embedding 请求的超时、速率限制和重试策略独立于 LLM 配置。
- 知识条目更新时异步重新生成向量（通过 Celery 低优先级任务）。

#### 12.5.3 RAG 上下文注入规则

ContextAssembler 在组装 AI 角色上下文时按以下优先级注入检索结果：

1. **阶段前置**：在该阶段所有角色任务启动前，对项目整体技术栈执行一次全局检索，注入阶段级 System Prompt。
2. **角色前置**：在单个角色任务启动前，对当前源码片段/候选漏洞执行针对性检索，注入角色级上下文。
3. **工具触发**：角色在分析过程中可主动调用 `search_security_knowledge` 工具进行补充检索（受调用次数限制）。

注入格式：

```text
[检索上下文 - 来自安全知识库]
相关漏洞模式（相似度 0.92）：SQL 注入 - 未使用参数化查询
  > 危险模式：字符串拼接构造 SQL 语句
  > 参考修复：使用 PreparedStatement 或 ORM 参数绑定
  > 来源：OWASP Top 10 A03:2021 - Injection

相关安全规范（相似度 0.87）：输入校验最佳实践
  > 所有外部输入在进入 SQL 前必须经过类型校验和白名单过滤
  ...

[检索上下文结束]
```

#### 12.5.4 检索记录与效果追踪

每次 RAG 检索（无论是阶段前置、角色前置还是工具触发）必须写入 `knowledge_retrievals` 记录：

- `project_id`、`stage_id`、`worker_task_id`：关联到具体分析上下文。
- `query_text`：检索查询文本的脱敏摘要。
- `retrieved_entries`：召回的 `knowledge_entry_id` 列表及各自相似度分数。
- `top_score`、`avg_score`：用于检索质量监控。

检索记录仅供管理员分析 RAG 效果和优化知识库使用，不参与业务状态流转。检索失败不影响阶段和角色的正常执行——RAG 是增强而非必需，检索异常时角色在无知识增强的情况下继续分析。

#### 12.5.5 安全约束

- 知识库查询工具是角色唯一允许的数据库相关操作，但角色不直接访问数据库。
- 角色不能通过检索工具执行任意 SQL 或向量查询——检索参数由 Worker 的检索服务白名单化。
- 检索查询文本在写入日志和前必须脱敏（移除完整源码片段和敏感标识符）。
- 知识条目内容中可以包含代码示例，但不得包含真实项目的凭证、密钥和敏感路径。
- `knowledge_entries` 的向量字段不得通过 API 直接暴露。
- 知识库的管理操作（新增、编辑、禁用、删除）仅限管理员通过配置接口执行，AI 角色无权限。

## 13. Executor、文件与报告

### 13.1 Executor 内部协议

- Executor 只监听内部网络。
- Worker 调用必须携带可验证的内部服务身份、`request_id`、`project_id` 和 `runtime_id`。
- 请求和响应使用 Pydantic Schema 和协议版本。
- 只提供容器创建、启动、停止、销毁、文件读取、目录遍历、关键字搜索和受控命令等预定义操作。
- 不提供任意 Docker API、宿主机 Shell 和绝对路径接口。
- 操作结果包含稳定错误码，不向 Worker 暴露 Docker SDK 原始异常。

### 13.2 路径安全

- 所有路径先规范化为项目根目录内相对路径。
- 使用真实路径校验符号链接解析后仍位于允许根目录。
- 拒绝绝对路径、独立 `..` 段、空字节和路径编码绕过。
- 用户输入不得直接拼接 `runtime_logs/`、`reports/`、`workspace/` 和 `repositories/` 的宿主机根路径。
- 文件读取、目录遍历、搜索结果和命令输出都有大小上限。

### 13.3 命令安全

- 命令使用程序名和参数数组，不拼接 Shell 字符串。
- 程序、参数、工作目录、环境变量、超时和输出上限分别校验。
- 模型不能直接决定可执行程序白名单。
- 容器进程使用非 root 用户、只读根文件系统和最小 Capabilities。
- 启用 `no-new-privileges`、Seccomp、进程数、CPU、内存、磁盘和超时限制。
- 默认禁止外网，临时开放必须匹配阶段策略和域名白名单。
- 日志记录策略结果、退出码和耗时，敏感参数先脱敏。

### 13.4 ArtifactStorage

- 所有文件通过 `ArtifactStorage` Port 读写。
- 业务层只保存逻辑键，不感知宿主机绝对路径。
- 写入采用临时文件、校验和原子替换，避免半文件被读取。
- 文件写入成功后计算 SHA-256、大小和媒体类型并保存 `file_artifacts`。
- 删除数据库元数据不等于删除物理文件。
- 后续迁移对象存储时不得改变业务用例。

### 13.5 报告

- 报告从数据库持久化快照生成，不依赖前端状态和临时聊天上下文。
- Jinja2 模板输入使用结构化对象，不把模型自由文本当作模板代码。
- Markdown-it-py 转换 HTML 后必须使用允许列表清理器过滤脚本、事件属性和危险 URL。
- Markdown、HTML 和下载文件写入 `reports/{project_id}/` 对应逻辑键。
- 数据库保存报告状态、版本、正文、逻辑键、摘要和错误。
- 文件成功落盘并校验后才能将报告置为 `ready`。
- 报告失败不得删除已保存漏洞和攻击路径。

### 13.6 删除与清理

项目删除按以下顺序执行：

1. 拒绝 `running` 项目。
2. 校验确认名称和幂等键。
3. 销毁运行容器。
4. 按逻辑键清理报告、证据、日志和工作目录。
5. 全部外部资源成功后删除项目行。
6. 依赖外键级联清理业务数据，保留脱敏审计。

部分清理失败时不得删除项目行，不得返回虚假成功。失败项必须可诊断并允许使用原幂等键重试。

## 14. 实时事件与 WebSocket

### 14.1 Event Relay

- Event Relay 只读取 `domain_events` 并发布到项目 Redis Stream。
- 按批次领取并限制单次处理数量。
- 发布消息包含 `event_id`、`sequence`、`event_type`、`project_id`、`occurred_at` 和 `data`。
- Redis 发布成功后再标记数据库事件为 `published`。
- 发布状态更新失败可能造成重复投递，消费者必须按 `event_id` 去重。
- Event Relay 不修改项目、阶段和任务状态。

### 14.2 WebSocket 握手

- 路径固定为 `/api/v1/projects/{project_id}/stream`。
- 校验 `asa_session` Cookie、Origin、项目 UUID 和项目权限。
- 支持 `asa.v1` 子协议和 `after_sequence`。
- 握手失败使用接口文档规定的 HTTP 状态和业务码。
- 单个连接只订阅一个项目，不接受客户端任意切换 Stream。

### 14.3 推送与续传

- 服务端按项目 `sequence` 顺序发送。
- `after_sequence` 仍在保留窗口时从下一事件续传。
- 超出保留窗口使用 `4009 EVENT_GAP_TOO_LARGE` 关闭，要求客户端 REST 补偿。
- 服务端提供应用层 `ping`、`pong`、空闲超时和会话失效检查。
- 每连接设置有界发送缓冲，慢客户端使用 `4010 CLIENT_TOO_SLOW` 关闭。
- 日志高峰可合并资源采样事件，但不得合并或改变状态、漏洞和报告事件语义。
- Redis 或 WebSocket 失败不得回滚数据库业务事务。

### 14.4 事件兼容

- 事件类型和最小载荷以 API 接口文档为准。
- 已发布字段不得在 `asa.v1` 中改变类型和含义。
- 新增可选字段必须保持旧客户端可忽略。
- 删除字段、改名或改变必填性需要新协议版本。
- 每种事件必须有序列化、反序列化和兼容性测试。

## 15. 异常处理

### 15.1 异常分类

| 类型 | 处理方式 |
| --- | --- |
| 输入校验错误 | 返回 `422` 和字段错误 |
| 认证失败 | 返回 `401` |
| 权限或 CSRF 失败 | 返回 `403` 并审计 |
| 资源不存在 | 返回 `404` |
| 状态、容量和版本冲突 | 返回 `409` |
| 限流 | 返回 `429` 和重试时间 |
| 依赖暂时不可用 | 返回 `503` |
| 未预期异常 | 返回 `500 INTERNAL_ERROR` |

### 15.2 异常传播

- 领域层抛领域异常。
- 应用层补充安全业务上下文，不转换为 HTTP Response。
- Infrastructure 把驱动和供应商异常转换为稳定基础设施异常。
- API 全局异常处理器映射状态码和业务码。
- Worker 根据异常类别决定失败、重试或停止。
- Router 和 Task 禁止捕获 `Exception` 后静默成功。

### 15.3 错误信息

- 响应只包含用户可理解的信息和 `request_id`。
- 服务端日志保存受控堆栈和链路字段。
- 不返回 SQL、数据库连接串、Python 文件路径、容器 Socket、命令敏感参数、密钥和完整第三方响应。
- 相同异常只在最合适边界记录一次，避免重复堆栈。
- 错误摘要写入数据库前必须长度受控和脱敏。

## 16. 日志、指标与可观测性

### 16.1 结构化日志

所有服务输出 JSON 日志，通用字段包括：

- `timestamp`
- `level`
- `service`
- `environment`
- `message`
- `request_id`
- `project_id`
- `runtime_id`
- `stage_id`
- `worker_task_id`
- `event_id`
- `error_type`

不存在的字段省略，不使用空字符串。日志级别只使用 `debug`、`info`、`warning`、`error`。

### 16.2 日志规则

- 请求完成记录方法、规范化路径、状态码和耗时，不记录 Cookie 和完整请求体。
- 登录失败、权限拒绝、任务重试、Executor 策略拒绝和文件完整性错误使用明确事件名。
- 高频运行日志写入 `runtime_logs` 时批量提交，避免每行独立事务。
- 敏感键递归脱敏，不能只处理顶层字典。
- 模型输入输出不记录完整正文。
- 生产环境不使用 `print`、`pprint` 和无结构堆栈。

### 16.3 指标

至少采集：

- API 请求量、状态码、P95 延迟和活动请求。
- WebSocket 连接数、重连、关闭码和发送缓冲。
- Celery 队列长度、任务耗时、成功、失败和重试。
- 阶段和角色任务耗时。
- Executor 容器创建、命令耗时、超时和策略拒绝。
- PostgreSQL 连接池、慢查询和事务回滚。
- Outbox 待发布数量、最老事件年龄和发布失败。
- 模型请求、错误、限流和 token。
- 项目容器 CPU 和内存。

指标标签不得包含用户名、完整项目名、文件路径、漏洞标题等高基数或敏感内容。

### 16.4 链路关联

`request_id` 从 API 传播到 Celery、Worker、Executor、审计和事件。后台主动任务生成新的根请求标识，并保留触发任务标识。不得依赖进程本地变量跨任务传播上下文。

## 17. 安全规范

### 17.1 输入和输出

- 所有 UUID 在进入 Repository 前校验。
- 状态和类型使用闭集。
- 字符串执行长度、空白和编码校验。
- 路径、URL、JSONB 和命令使用专用校验器。
- 日志、消息、证据和报告进入响应前再次脱敏。
- 输出 Schema 使用字段白名单，禁止直接序列化 `__dict__`。

### 17.2 注入防护

- SQL 只使用 SQLAlchemy 参数绑定，不拼接用户输入。
- Shell 命令使用参数数组并由 Executor Policy 校验。
- Jinja2 模板固定且不允许用户上传。
- Markdown 转 HTML 后执行允许列表清理。
- Git URL 禁止内联用户名密码、Token 和敏感查询参数。
- 文件路径解析后再次检查项目根目录。

### 17.3 服务边界

- PostgreSQL、Redis、Executor 和 Docker Engine 不暴露公网端口。
- API 数据库账户不具备 schema owner、扩展管理和超级用户权限。
- DDL 账户与运行账户分离。
- API、Worker 和 Executor 使用不同服务身份。
- Executor 内部认证失败必须拒绝并记录安全日志。
- CORS、Trusted Host、代理头和 Cookie Secure 策略由部署环境显式配置，不使用开放通配符。

### 17.4 限流

登录、初始化、项目写操作、配置更新、报告下载和 WebSocket 重连必须限流。限流键不得只依赖可伪造头。阈值由容量和安全评审确定，不在业务代码分散写死。

### 17.5 依赖与供应链

- 锁文件和镜像基础版本纳入评审。
- 定期执行依赖漏洞扫描。
- 镜像使用固定摘要并以非 root 用户运行。
- 构建产物不包含测试密钥、`.env`、Git 元数据和本地缓存。
- 安全升级不得与大规模功能改动混在同一变更中。

## 18. 性能与可靠性

### 18.1 API 性能

- 普通查询服务端 P95 不超过 2 秒。
- 创建、启动和停止在 3 秒内返回受理或明确失败。
- 长任务只返回 `202`，不在 HTTP 请求中等待源码拉取、容器、模型和报告。
- 列表查询使用字段裁剪、稳定分页和匹配索引。
- 慢查询必须用真实 PostgreSQL 数据和 `EXPLAIN ANALYZE` 定位，不以扩大连接池掩盖问题。

### 18.2 连接与资源

- 数据库、Redis、HTTP 和模型客户端设置连接池、连接超时、读取超时和总时限。
- 超时值集中配置，不使用库的无限默认值。
- 单请求、单任务、单命令和单文件均有大小或时间上限。
- API 不持有跨请求 Session。
- Worker 子进程不复用不安全的父进程数据库连接。

### 18.3 批量与背压

- 日志、资源和 Outbox 使用有上限批量写入。
- WebSocket 使用有界缓冲并断开慢客户端。
- 模型、Executor 和文件输出超过上限时截断并明确记录。
- 项目并发达到配置上限时拒绝新启动，不建立无限队列。
- 清理任务小批次执行，避免长事务和大范围锁。

### 18.4 恢复

- 服务重启后从 PostgreSQL 恢复项目和任务状态。
- WebSocket 和 Redis 丢失不影响已提交业务结果。
- Worker 启动时扫描异常停留的 `running` 任务，结合心跳和容器状态进入可诊断恢复流程。
- 不自动把不确定任务标记为成功。
- 报告失败保留漏洞和攻击路径。
- 文件清理失败保留项目行和失败项。

## 19. 测试规范

### 19.1 测试分层

| 层级 | 依赖 | 重点 |
| --- | --- | --- |
| 单元测试 | Fake、Stub | 领域状态机、权限、幂等、校验和纯函数 |
| 应用测试 | Fake Repository、Fake Port | 用例、事务边界、事件和异常 |
| API 测试 | FastAPI、HTTPX | 路由、Schema、状态码、Cookie 和错误码 |
| 契约测试 | OpenAPI、事件 Schema | 请求响应、事件和内部协议兼容 |
| 数据库集成 | Testcontainers PostgreSQL | 约束、锁、事务、迁移和查询 |
| 中间件集成 | Testcontainers Redis | Outbox 发布、Stream 和取消信号 |
| 端到端 | 真实进程和受控替身 | 初始化、项目、调度、结果和报告主链路 |

### 19.2 单元测试

必须覆盖：

- 项目全部合法和非法状态迁移。
- 阶段顺序、关键任务失败和停止收敛。
- 普通用户、管理员和项目归属权限。
- 幂等首次请求、同 Key 重试和 Key 冲突。
- 路径、仓库 URL、命令参数和逻辑键校验。
- 漏洞指纹和并发去重。
- 攻击路径步骤连续性。
- 模型输出 Schema 和非法输出。
- 错误映射、脱敏和日志字段。

测试名称描述给定条件、行为和预期结果。时间、UUID、随机退避和外部响应使用可注入依赖，不在测试中使用真实等待。

### 19.3 API 测试

每个接口至少覆盖：

- 成功响应和统一响应结构。
- 请求体、路径和查询参数校验。
- 未登录、会话过期、CSRF 和权限拒绝。
- 资源不存在和状态冲突。
- 幂等和重复提交。
- 限流响应。
- 未预期异常不会泄露内部信息。

报告下载额外测试媒体类型、文件名、权限、文件缺失和摘要不匹配。WebSocket 额外测试握手、心跳、续传、重复事件、`4009` 和慢客户端关闭。

### 19.4 数据库与迁移测试

- 在临时 PostgreSQL 上从空库执行 `alembic upgrade head`。
- 验证初始化 SQL 与 Migration 的 schema 一致性。
- 测试主键、外键、唯一、CHECK、部分索引和延迟约束。
- 测试项目级复合外键拒绝跨项目关联。
- 测试状态更新竞争只有一个事务成功。
- 测试 Outbox 事件与业务状态同事务提交和回滚。
- 测试配置唯一生效和攻击路径连续步骤。
- 迁移涉及存量数据时提供升级数据夹具。

### 19.5 Worker 与 Executor 测试

- Worker 测试重复投递、有限重试、取消检查、失败收敛和恢复扫描。
- AI 适配使用 Fake 模型，不在普通测试调用真实收费服务。
- Executor 测试允许命令、拒绝命令、路径穿越、符号链接逃逸、超时、输出上限和资源限制。
- 容器集成测试使用专用无敏感数据镜像，不挂载宿主机真实源码和密钥目录。
- 清理测试验证部分失败可重试且不提前删除项目。

### 19.6 覆盖率

- 后端总体行覆盖率和分支覆盖率均不得低于 80%。
- 项目状态机、权限、幂等、路径安全和命令策略必须覆盖全部已定义分支。
- 覆盖率不能替代有效断言。
- 修复缺陷必须增加可复现测试；无法自动化时说明原因、人工步骤和后续任务。

## 20. API 与协议文档

### 20.1 OpenAPI

- FastAPI Router 必须声明稳定 `operation_id`。
- 请求头、路径、查询、请求体、响应、状态码和错误码均进入 OpenAPI。
- Pydantic 字段提供准确描述、约束和真实示例。
- Cookie 认证、CSRF、幂等头和文件响应必须在文档中明确。
- 内部字段和敏感 Schema 不得出现在公开 OpenAPI。
- 生成的 OpenAPI 文件纳入版本控制和契约差异检查。

### 20.2 接口文档同步

新增或修改接口时必须同步更新 `docs/4_开发规范/API接口文档.md`，至少包含：

- 接口名称和用途。
- 请求方式和 URL。
- 认证方式和请求头。
- 路径参数、查询参数和请求体。
- 成功与失败响应示例。
- HTTP 状态码和业务错误码。
- 幂等、权限、安全和异步注意事项。

数据库字段、状态值和事件载荷变化还必须同步更新数据库设计、字段规范、前端契约和测试。

### 20.3 内部协议

Worker 到 Executor、Celery Task 和实时事件都必须有版本化 Pydantic Schema。内部协议同样执行契约测试，不以“内部调用”为理由传递无结构字典。

## 21. 质量门禁

### 21.1 标准命令

根 `pyproject.toml` 必须配置统一工具规则。后端变更合并前至少执行：

```bash
python -m ruff format --check apps packages tests
python -m ruff check apps packages tests
python -m mypy apps packages
python -m pytest tests/unit tests/api tests/contract
python -m pytest tests/integration
python -m pytest tests/e2e
python -m alembic upgrade head
```

`alembic upgrade head` 必须指向一次性测试数据库，禁止把质量检查命令直接连接开发共享库或生产库。接口或数据库变更还必须执行 OpenAPI 生成差异检查、初始化 SQL 对比和迁移约束测试。命令可由仓库脚本封装，但不得改变检查职责。

### 21.2 禁止合并

以下任一情况不得合并：

- Ruff 格式或静态检查失败。
- mypy 存在错误。
- 单元、接口、契约、集成或必要 E2E 失败。
- Migration 无法从空库升级或与设计不一致。
- OpenAPI 与实现不一致。
- 通过关闭规则、放宽类型、跳过测试或删除断言掩盖失败。
- P0 流程缺少错误、权限、冲突和恢复测试。
- 新增日志、事件或错误响应泄露敏感信息。

### 21.3 交付说明

每次后端交付必须说明：

- 关键改动和影响模块。
- API、数据库、任务、事件和内部协议变化。
- 已执行的格式化、静态检查、测试、迁移和契约命令及结果。
- 向后兼容性和部署顺序。
- 数据迁移、回滚和恢复方式。
- 安全、性能、容量和并发风险。
- 尚未覆盖的环境及需要联合确认的事项。

不得只写“无兼容性影响”或“无风险”。确实无已知影响时，应给出检查依据和未覆盖边界。

## 22. 兼容性规范

### 22.1 API 兼容

- `/api/v1` 内可新增可选响应字段和新接口。
- 不得删除字段、改变类型、重命名业务码或改变既有状态含义。
- 新增必填请求字段属于破坏性变更，必须提供过渡策略或新版本。
- 列表排序、分页和游标语义不得无通知改变。
- Cookie、CSRF 和幂等规则变化必须前后端联合评审。

### 22.2 数据库兼容

- 优先采用 Expand、Migrate、Contract 顺序。
- 应用必须在迁移发布窗口兼容新旧字段的合理过渡。
- 删除列、改类型、重建大索引和全表更新必须单独评审。
- 回退应用前确认数据库 schema 仍兼容旧版本。
- 状态值新增需要数据库、领域、API、前端和测试同步发布。

### 22.3 任务与事件兼容

- Worker 部署期间可能消费旧版本消息，任务 Schema 必须包含版本。
- 新 Worker 必须在过渡期兼容仍在队列中的受支持旧消息。
- 已发布实时事件字段不得改变含义。
- Executor 客户端和服务端协议升级必须具备兼容窗口或同步部署计划。
- 模型结构化输出 Schema 变化必须处理运行中任务的版本差异。

## 23. 已知风险与开发前置事项

以下事项尚未形成可直接编码的完整契约，开发前必须确认或补充设计：

- 当前接口缺少“当前用户与会话恢复”查询，页面刷新后无法可靠恢复用户角色。
- 现有 `worker_tasks.idempotency_key` 未显式保存操作类型、请求指纹和首次响应快照，尚不足以完整实现 API 规定的幂等重放语义。
- API 事务提交后 Celery 投递失败的待投递标识和恢复扫描条件需要明确。
- 异步删除失败项缺少面向管理员的查询入口和稳定状态表达。
- WebSocket 全量补偿后如何获得最新项目事件 `sequence` 尚未定义。
- 会话持久化、撤销、续期和多进程共享机制尚未确定。
- Worker 到 Executor 的内部认证和协议版本尚未形成详细设计。
- 私有仓库凭证托管、临时注入和销毁流程尚未确定。
- `chat_messages.message_type` 尚未定义闭集。
- 模型供应商、模型列表、token 预算和敏感源码出域策略尚未确认。
- 容器外网白名单、资源配额、命令白名单、并发数和保留周期缺少最终值。
- 运行中异常任务的心跳字段和人工诊断状态未在当前表结构中完整体现。
- Embedding 模型供应商、模型名称和向量维度尚未确认。
- pgvector 索引类型（IVFFlat/HNSW）和索引构建频率尚未确定。
- 安全知识库初始条目录入来源、审核流程和自动沉淀策略未定义。
- RAG 检索的 top-k 默认值、相似度阈值和各子库权重尚未确定。

未确认项不得通过硬编码、进程内状态、无约束 JSON 或临时 Redis Key 长期绕过。确需调整接口或表结构时，先更新设计文档、Migration 和契约测试。

## 24. 代码评审清单

### 24.1 架构

- 是否遵循 API、Worker、Executor 和共享核心的职责边界。
- Domain 是否保持框架无关。
- Router、Task 和 Repository 是否足够薄。
- 是否存在跨层反向依赖、循环依赖和重复状态机。
- 新抽象是否解决稳定重复问题，是否存在过度设计。

### 24.2 接口与权限

- 路径、状态码、业务码和统一响应是否符合 API 文档。
- Pydantic 是否拒绝未知字段并限制长度和值域。
- 项目及子资源是否在查询阶段应用权限范围。
- Cookie、CSRF、幂等和限流是否完整。
- 错误响应是否包含 `request_id` 且无敏感信息。

### 24.3 数据与任务

- 事务边界是否明确，外部调用是否位于事务外。
- 状态变化是否与 Outbox 同事务。
- 是否使用条件更新、唯一约束和锁处理并发。
- Celery 是否幂等、可取消、可恢复且有限重试。
- Migration、索引、查询和回退是否经过验证。

### 24.4 安全与可观测

- 路径、命令、模型输出和报告是否按不可信内容处理。
- 是否存在 SQL、Shell、模板、路径或 HTML 注入风险。
- 日志、审计、事件和指标是否脱敏并可关联。
- API 是否直接接触 Docker Socket 或宿主机路径。
- 是否设置超时、大小、连接池、队列和缓冲上限。

### 24.5 测试与交付

- 关键状态、权限、幂等、失败和恢复分支是否有测试。
- API 文档、OpenAPI、数据库设计和契约是否同步。
- Ruff、mypy、Pytest、Migration 和构建检查是否通过。
- 交付说明是否包含关键改动、兼容性影响和潜在风险。
