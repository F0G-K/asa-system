# 漏洞管理模块（vulnerabilities）

## 1. 模块概述

### 1.1 定位

`vulnerabilities` 模块负责安全评估发现的结构化漏洞管理——从代码分析角色输出的候选漏洞标准化、去重入库，到验证角色确认可达性，再到前端查询展示。漏洞数据是评估报告的核心输入。

### 1.2 设计依据

- `docs/1_PRD/自动化安全评估系统-PRD.md`
- `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md` — 第 5.2 节、第 8.6 节
- `docs/4_开发规范/API接口文档.md` — 第 7.1-7.2 节（漏洞列表与详情）
- `docs/4_开发规范/后端/后端开发规范.md` — 第 12.4 节（漏洞去重）
- `docs/4_开发规范/数据库/数据库设计.md` — `vulnerabilities` 表设计

### 1.3 职责边界

| 职责 | 说明 |
| --- | --- |
| 漏洞入库 | 接收 code_analyst 输出的候选漏洞，校验后持久化 |
| 漏洞去重 | 按项目、规则类型、文件路径、位置和证据指纹去重 |
| 验证管理 | 跟踪 `pending → verified/rejected` 的验证状态流转 |
| 证据保存 | 保存漏洞影响、触发条件、证据、复现步骤和验证代码 |
| 漏洞查询 | 提供分页列表（支持风险等级和验证状态筛选）和详情查询 |
| 编号生成 | 按项目生成 `ASA-YYYY-NNNN` 格式的漏洞编号 |

**不负责：** 漏洞发现（agents/code_analyst）、漏洞验证执行（agents/vulnerability_verifier）、攻击路径关联（attack_paths）——这些由对应模块处理。

| 接口 | 方法 | URL | 说明 |
| --- | --- | --- | --- |

| 查询漏洞详情 | `GET` | `/api/v1/projects/{project_id}/vulnerabilities/{vulnerability_id}` | 完整漏洞信息含证据和复现步骤 |

## 3. 领域模型

### 3.1 漏洞实体

```text
Vulnerability
├── id: UUID
├── project_id: UUID
├── discovered_by_task_id: UUID?          # 发现任务
├── verified_by_task_id: UUID?            # 验证任务
├── vuln_code: str                        # 漏洞编号，如 "ASA-2026-0004"
├── vuln_title: str                       # 漏洞标题
├── rule_type: str                        # 规则/漏洞类别
├── risk_level: "critical" | "high" | "medium" | "low" | "info"
├── file_path: str                        # 源码相对路径
├── line_start: int?                      # 起始行
├── line_end: int?                        # 结束行
├── impact_text: str                      # 漏洞影响
├── condition_text: str                   # 触发条件
├── evidence_text: str                    # 证据正文
├── evidence_fingerprint: str             # SHA-256 去重指纹
├── verify_status: "pending" | "verified" | "rejected"
├── reproduce_steps_text: str?            # 复现步骤
├── verify_code_text: str?                # 验证代码
├── created_at: datetime
└── updated_at: datetime
```

### 3.2 验证状态机

```text
pending → verified
       ↘ rejected
```

- `pending`：code_analyst 输出的候选漏洞，尚未验证。
- `verified`：vulnerability_verifier 确认可达性和触发条件。
- `rejected`：vulnerability_verifier 确认不可达、误报或条件不成立。

### 3.3 业务规则

| 规则 | 说明 |
| --- | --- |
| 漏洞编号项目内唯一 | `(project_id, vuln_code)` UNIQUE |
| 去重指纹项目内唯一 | `(project_id, evidence_fingerprint)` UNIQUE |
| 指纹 = SHA-256(rule_type + file_path + location + normalized evidence) | 集中实现，固定测试向量 |
| 风险等级排序固定 | `critical > high > medium > low > info` |
| 同等级稳定排序 | 使用 `(created_at, id)` 次键 |
| 必须校验漏洞属于路径中的 project_id | 禁止跨项目访问 |
| 证据指纹不通过 API 返回 | 仅内部去重实现用 |
| 发现/验证任务删除不影响漏洞 | 外键 `ON DELETE NO ACTION` |

### 3.4 领域异常

| 异常 | HTTP 状态 | 业务码 |
| --- | --- | --- |
| `VulnerabilityNotFound` | 404 | `VULNERABILITY_NOT_FOUND` |
| `VulnerabilityDuplicate` | 内部处理 | 合并而不是报错 |

## 4. 漏洞去重机制

### 4.1 指纹算法

```text
evidence_fingerprint = SHA-256(
    rule_type +
    "|" +
    normalized_file_path +
    "|" +
    "L" + line_start + "-" + line_end +
    "|" +
    normalized_evidence_text
)

规范化规则：
  - file_path: 去除首尾空白、统一路径分隔符为 /
  - evidence_text: 去除首尾空白、移除时间戳和随机值
```

### 4.2 去重流程

```text
code_analyst 输出候选漏洞
  │
  ├── 1. Pydantic Schema 校验
  ├── 2. 路径范围校验（文件路径在项目内）
  ├── 3. 风险等级校验（属于定义内值）
  ├── 4. 计算 evidence_fingerprint
  ├── 5. 检查项目内 fingerprint 是否存在
  │     ├── 不存在 → INSERT 新漏洞 (verify_status='pending')
  │     └── 存在 → 读取已有记录，安全合并字段
  │           （保留原有验证状态，更新标题和影响描述）
  └── 6. 唯一约束作为并发兜底
```

### 4.3 并发去重

- 数据库 `(project_id, evidence_fingerprint)` UNIQUE 约束。
- 唯一冲突时不报错，读取已有记录并合并。
- 合并不覆盖已有的 `verify_status`（避免覆盖验证结论）。

## 5. 查询实现

### 5.1 漏洞列表

```text
GET /api/v1/projects/{project_id}/vulnerabilities
  ?page=1&page_size=20
  &risk_level=critical&risk_level=high
  &verify_status=verified
  &keyword=越权
  &file_path=app/api/
  &sort=risk_level:desc

查询条件：
  ├── WHERE project_id = :project_id   ← 项目范围
  ├── AND risk_level IN (:levels)      ← 可选
  ├── AND verify_status IN (:statuses) ← 可选
  ├── AND (vuln_code ILIKE :kw OR vuln_title ILIKE :kw) ← 可选
  └── AND file_path LIKE :prefix%      ← 可选

排序：
  risk_level:desc → 固定映射 critical=1, high=2, ... + (created_at, id)
  created_at:asc/desc

索引：ix_vulnerabilities__project_id_risk_verify
```

### 5.2 漏洞详情

```text
GET /api/v1/projects/{project_id}/vulnerabilities/{vulnerability_id}

校验：
  ├── project_id 是有效 UUID
  ├── vulnerability_id 是有效 UUID
  └── 漏洞的 project_id 与路径 project_id 一致 ← 防止跨项目访问

返回：完整漏洞信息（含 evidence_text、reproduce_steps_text、verify_code_text）
不返回：evidence_fingerprint（内部实现字段）
```

## 6. 代码实现指南

### 6.1 目录结构

```text
packages/backend-core/src/asa_core/domain/vulnerabilities/
├── entities.py              # Vulnerability 聚合根
├── fingerprint.py           # 去重指纹算法
├── risk_level.py            # RiskLevel 枚举和排序
├── value_objects.py         # VulnCode, FileLocation
└── exceptions.py            # VulnerabilityNotFound

packages/backend-core/src/asa_core/application/
├── commands/
│   ├── create_vulnerability.py   # CreateVulnerability (含去重逻辑)
│   └── update_verification.py    # UpdateVerification
├── queries/
│   ├── list_vulnerabilities.py   # ListVulnerabilities
│   └── get_vulnerability_detail.py # GetVulnerabilityDetail
└── ports/
    └── vulnerability_repository.py

apps/api/src/asa_api/routers/v1/vulnerabilities.py
apps/api/src/asa_api/schemas/vulnerabilities.py
```

### 6.2 关键实现约束

- **去重指纹算法集中实现**，有固定测试向量。不在多处复制指纹逻辑。
- **写操作使用数据库 UNIQUE 约束兜底**，不用"先查再写"作为唯一并发保护。
- **唯一冲突时合并而非报错**：捕获 `IntegrityError` → 查询已有记录 → 安全合并字段。
- **校验漏洞与路径中的 project_id 一致**：Repository 层查询条件同时包含两个 UUID。
- **证据、复现步骤和验证代码按纯文本返回**，前端不得直接作为 HTML 执行。
- 响应不返回 `evidence_fingerprint` 等内部实现字段。
- 漏洞数据写入前执行业务校验：路径在项目范围内、风险等级有效、非空必填字段。

## 7. 安全要点

- 所有漏洞查询同时校验 `project_id` 和当前用户权限（`projects.created_by`）。
- `vulnerability_id` 单独存在不表示用户有访问权限，必须结合项目归属判断。
- 证据文本（`evidence_text`、`reproduce_steps_text`、`verify_code_text`）在前端渲染前进行安全转义，不直接作为 HTML 执行。
- 漏洞详情不泄露发现任务的完整模型提示词或内部密钥。

## 8. 测试要点

### 8.1 单元测试

- 去重指纹算法：相同内容生成相同指纹，不同内容生成不同指纹
- 规范化规则：路径分隔符统一、空白去除
- 风险等级排序：`critical > high > medium > low > info`
- 漏洞编号格式校验
- 并发去重：唯一冲突时的合并逻辑（不覆盖验证状态）

### 8.2 API 测试

- `GET /api/v1/projects/{project_id}/vulnerabilities` — 分页、多风险等级筛选、多验证状态筛选、关键词搜索、文件路径前缀筛选、空结果
- `GET /api/v1/projects/{project_id}/vulnerabilities/{id}` — 成功、漏洞不存在（404）、跨项目访问（404/403）
- 响应不包含 `evidence_fingerprint`
- 项目权限过滤：用户 A 不能看到用户 B 项目的漏洞

### 8.3 数据库集成测试

- `(project_id, vuln_code)` UNIQUE 约束
- `(project_id, evidence_fingerprint)` UNIQUE 约束
- 外键级联：删除项目 → 漏洞同步删除
- 发现任务删除不影响漏洞（NO ACTION）
