# 自动化安全评估系统数据库设计

## 1. 设计目标与依据

本设计覆盖自动化安全评估系统 MVP 的 16 张数据表，直接指导 SQLAlchemy 2 Model、Alembic migration、查询服务和数据一致性测试。PostgreSQL 是项目、阶段、角色任务、漏洞、攻击路径、报告、日志、资源、审计和实时事件的唯一业务事实源；Redis Stream、Celery 消息和 WebSocket 仅承担传输或短期缓存职责。

设计依据按优先级为：

1. `docs/1_PRD/自动化安全评估系统-PRD.md`
2. `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md`
3. `docs/0_draft/1.4 自动化安全评估系统.md`
4. `README.md`
5. `deploy/prompt.md`

字段表中的来源缩写如下：

| 缩写 | 来源 |
| --- | --- |
| 原始 | 原始需求 `1.4.8 数据表要求` |
| PRD | PRD 功能、数据或非功能需求 |
| 概要 | 概要设计中的数据、事务、安全或可观测性要求 |
| 细化 | 为落实上层需求补充的字段级设计 |

## 2. 技术约定

### 2.1 数据库与 schema

- 数据库使用 PostgreSQL 15 及以上，业务对象位于 `public` schema。
- 使用 `pgcrypto` 的 `gen_random_uuid()` 生成业务 UUID。
- 使用 `pgvector` 扩展（0.5 及以上）存储安全知识 Embedding 向量并支持 ANN 检索。
- ORM 使用 SQLAlchemy 2 typed declarative mapping。
- 结构版本使用 Alembic 管理，禁止应用启动时隐式建表或改表。
- 所有时间使用 `timestamptz`，数据库和应用统一按 UTC 写入，API 输出带时区的 ISO 8601。

### 2.2 主键策略

| 类型 | 适用表 | 原因 |
| --- | --- | --- |
| UUID | `users`、`projects`、`project_runtimes`、`runtime_stages`、`worker_tasks`、`vulnerabilities`、`attack_paths`、`reports`、`system_configs`、`file_artifacts` | 对外暴露、跨进程创建或需要不可枚举标识 |
| BIGINT IDENTITY | `attack_path_items`、`chat_messages`、`runtime_logs`、`resource_usages`、`audit_logs`、`domain_events` | 内部有序追加、写入频繁、按游标分页 |

所有表的主键字段均命名为 `id`。`domain_events.event_id` 是对外去重 UUID，不能使用内部主键替代。

### 2.3 通用字段策略

- 可变业务表使用 `created_at`、`updated_at`，由统一 trigger 维护 `updated_at`。
- 追加型记录只保留业务时间字段，不机械增加 `updated_at`。
- 状态使用 `varchar` 与命名 `CHECK`，不使用 PostgreSQL 原生 ENUM。
- 大文本使用 `text`；仅配置快照、事件载荷和脱敏扩展元数据使用 `jsonb`。
- 文件字段保存 `ArtifactStorage` 逻辑键或项目内相对路径，禁止绝对路径和 `..` 路径段。
- SHA-256 使用 64 位小写十六进制 `char(64)`。
- 数据库不保存明文密码、认证 Cookie、Git 凭证、模型密钥、Token 或证书。

## 5. 表结构详细设计

### 5.1 `users`

用途：保存管理员和普通使用者的登录标识、Argon2id 密码哈希及账户状态。

| 字段 | PostgreSQL 类型 | 可空 | 默认值 | 键或约束 | 说明 | 来源 |
| --- | --- | :---: | --- | --- | --- | --- |
| `id` | `uuid` | 否 | `gen_random_uuid()` | PK | 用户标识 | 原始 |
| `username` | `varchar(64)` | 否 | 无 | UK，规范化检查 | 小写且无空白的登录名 | 原始、细化 |
| `password_hash` | `varchar(255)` | 否 | 无 | 长度检查 | Argon2id 哈希 | 原始、PRD |
| `role` | `varchar(32)` | 否 | 无 | CHECK | 用户角色 | 原始、PRD |
| `status` | `varchar(32)` | 否 | `active` | CHECK | 账户状态 | 原始 |
| `created_at` | `timestamptz` | 否 | `CURRENT_TIMESTAMP` |  | 创建时间 | 原始 |
| `updated_at` | `timestamptz` | 否 | `CURRENT_TIMESTAMP` | trigger | 更新时间 | 细化 |

主键为 `pk_users`，用户名由 `uq_users__username` 唯一。用户名在写入前转为小写，数据库再次检查。`projects.created_by` 和 `system_configs.updated_by` 使用 `RESTRICT`，MVP 未提供用户删除功能。典型查询是登录名精确查找；数据量低，不需要额外索引。

### 5.2 `projects`

用途：保存源码接入信息、任务说明、隔离环境类型和项目权威状态。

| 字段 | PostgreSQL 类型 | 可空 | 默认值 | 键或约束 | 说明 | 来源 |
| --- | --- | :---: | --- | --- | --- | --- |
| `id` | `uuid` | 否 | `gen_random_uuid()` | PK | 项目标识 | 原始 |
| `project_name` | `varchar(128)` | 否 | 无 | 非空检查 | 项目名称 | 原始 |
| `source_type` | `varchar(32)` | 否 | 无 | CHECK | `local` 或 `repository` | 原始、PRD |
| `source_path` | `text` | 否 | 无 | 路径与凭证检查 | 相对路径或脱敏仓库地址 | 原始、PRD |
| `task_content` | `text` | 否 | 无 | 非空检查 | 评估任务说明 | 原始 |
| `environment_type` | `varchar(64)` | 否 | 无 | 格式检查 | 管理员启用的环境类型 | PRD、细化 |
| `project_status` | `varchar(32)` | 否 | `created` | CHECK | 项目状态 | 原始、PRD |
| `created_by` | `uuid` | 否 | 无 | FK | 创建用户 | 原始 |
| `stop_requested_at` | `timestamptz` | 是 | 无 |  | 项目级取消标记 | 概要 |
| `last_started_at` | `timestamptz` | 是 | 无 |  | 最近一次运行开始时间，由 `project_runtimes.started_at` 同步 | 细化 |
| `last_finished_at` | `timestamptz` | 是 | 无 |  | 最近一次运行结束时间，由 `project_runtimes.stopped_at` 同步 | 细化 |
| `created_at` | `timestamptz` | 否 | `CURRENT_TIMESTAMP` |  | 创建时间 | 原始 |
| `updated_at` | `timestamptz` | 否 | `CURRENT_TIMESTAMP` | trigger | 更新时间 | 原始 |

`last_started_at` 和 `last_finished_at` 为冗余字段，在运行实例状态变更时由领域服务同步写入，用于项目列表直接展示最近运行摘要，避免每次列表查询都需要 JOIN `project_runtimes`。这两个字段不参与状态机判定。

外键 `created_by → users.id` 使用 `ON DELETE RESTRICT`。索引 `ix_projects__created_by_created_at` 支持用户项目列表，`ix_projects__project_status_updated_at` 支持状态筛选和异常运行扫描。源码地址不保存内联密码；本地地址保存授权根目录内相对路径。项目删除由业务清理任务发起，成功删除项目行后关联业务数据级联删除。

## 8. 事务与一致性设计

### 8.1 项目启动

1. 以项目行锁或项目 ID advisory lock 串行化启动。
2. 条件更新仅允许 `created → running` 的准备流程；环境未成功前可保持 `created`，失败后转 `failed`。
3. 创建唯一 `project_runtimes` 记录和 5 条 `runtime_stages`。
4. 创建首个 `worker_tasks` 并写入项目内唯一幂等键。
5. 每次权威状态变更与相应 `domain_events` 在同一事务提交。

`project_runtimes.project_id` 唯一、条件更新和任务幂等索引共同防止重复启动。

### 8.2 Outbox

领域服务取得项目级锁后分配 `sequence = 当前最大值 + 1`，写业务表和 `domain_events` 后一起提交。`event-relay` 使用 `FOR UPDATE SKIP LOCKED` 批量领取待投递事件，成功后置为 `published`，失败后记录 `failed`、`last_error`、`retry_count` 和 `next_retry_at`。消费者按 `event_id` 去重，WebSocket 按 `(project_id, sequence)` 续传。

### 8.3 状态更新

数据库只负责值域、时间完整性、引用完整性和唯一性。项目与阶段状态机由领域服务控制，不使用复杂触发器实现业务流转。更新状态时使用期望旧状态条件，例如：

```sql
UPDATE projects
SET project_status = 'running'
WHERE id = :project_id
  AND project_status = 'created';
```

受影响行数不是 `1` 时返回 `409 Conflict`。

### 8.4 攻击路径

路径和全部步骤必须在同一事务创建。延迟唯一约束允许事务内重排，两个延迟约束触发器在提交时保证至少一个步骤且 `step_order` 从 `1` 连续。复合外键保证路径与漏洞属于同一项目。

### 8.5 配置切换

配置采用版本化追加。事务内锁定当前生效配置，将旧记录 `is_active` 置为 `false`，创建或激活新版本，再写审计日志。部分唯一索引防止双活。

## 9. 删除、文件与审计

项目删除是外部资源与数据库协同清理，不是单条 SQL：

1. 拒绝删除 `running` 项目。
2. 记录带幂等键的删除请求和审计。
3. 销毁运行容器。
4. 按 `file_artifacts.logical_key` 清理报告、证据、归档日志和工作目录。
5. 全部外部资源成功后删除 `projects` 行，由外键级联清理业务数据。
6. `audit_logs.project_id` 自动置空，保留脱敏 `object_id` 和结果。

部分清理失败时不得删除项目行，应记录失败项并允许同一幂等键重试。数据库删除文件元数据不会删除物理文件。

## 10. 查询、容量与保留

- `runtime_logs`、`chat_messages` 和 `resource_usages` 使用 `(时间, id)` 稳定游标，不允许无边界全量查询。
- 日志和资源接口必须带项目权限、时间范围和条数上限。
- MVP 不预先分区。单表持续超过约千万级记录、索引无法维持目标延迟或清理出现长事务时，再按月对 `runtime_logs`、`resource_usages`、`audit_logs` 和 `domain_events` 评估范围分区。
- 保留天数来自唯一生效 `system_configs`；未确认时不自动清理。
- 清理任务按小批次删除并记录审计，避免长事务和大范围锁。
- 报告正文可在 MVP 保存在 PostgreSQL；大证据和归档日志只保存摘要及文件逻辑键。

## 11. 安全设计

- `password_hash` 仅保存 Argon2id 哈希，初始化 SQL 不创建账户。
- 仓库地址进入数据库前移除内联密码；Git 凭证由受控密钥系统临时注入。
- JSONB 写入采用字段白名单和递归敏感键过滤。
- `source_path`、`file_path`、`logical_key` 和报告文件键在应用与数据库双重校验。
- 普通用户查询统一附加 `projects.created_by = current_user_id`；跨用户授权表尚未定义，不以管理员权限替代资源审计。
- 报告、证据、日志和 WebSocket 建连均先校验项目访问权限。
- 数据库应用账户不应具有扩展、schema owner 或超级用户权限；DDL 账户与运行账户分离。

## 12. SQLAlchemy 与 Alembic

- UUID 字段使用 `Mapped[uuid.UUID]` 与 `Uuid(as_uuid=True)`。
- `timestamptz` 使用 `DateTime(timezone=True)`。
- JSONB 使用 PostgreSQL `JSONB`，数组使用 `ARRAY(String(64))`。
- BIGINT IDENTITY 使用 `BigInteger` 与 `Identity(always=True)`。
- 向量字段使用 pgvector 的 `Vector` 类型，维度在 Migration 中以注释标注。
- 复合候选键、复合外键、部分索引、延迟唯一约束和约束触发器必须显式写入 Alembic。
- 首个 migration 应与 `初始化sql.md` 同源生成，包含 `CREATE EXTENSION IF NOT EXISTS vector` 和 `CREATE EXTENSION IF NOT EXISTS pgcrypto`，并在临时 PostgreSQL 上执行升级、约束拒绝用例和 schema diff。
- 迁移禁止在高频表上无评估地执行全表重写；新增非空字段采用“可空列、回填、加约束”的分阶段方式。
- IVFFlat 向量索引在数据回填 `embedding` 列后单独创建，不在建表 Migration 中自动生成。

## 14. 设计假设与待确认事项

- `users.role` 使用 `user`、`admin`，`users.status` 使用 `active`、`disabled`；需求仅定义中文角色和状态字段，技术值需评审确认。
- `project_runtimes.container_status`、`reports.report_status`、`audit_logs.result_status`、`domain_events.publish_status` 和 `file_artifacts.artifact_type` 是为落实概要流程补充的闭集，需后端协议评审。
- `chat_messages.message_type` 未定义闭集，当前只校验非空，待角色消息协议确定后通过 migration 增加 CHECK。
- MVP 按需求禁止原地重跑，因此每项目只能有一条 `project_runtimes`；未来支持重跑时需要调整唯一约束和查询语义。
- 普通用户之间的项目共享规则尚未确定，本设计不新增授权表，当前按创建者归属控制。
- 本地源码授权根目录、私有仓库凭证托管、外网白名单、资源配额、并发数和保留天数均由部署及安全评审确定。
- 漏洞指纹规范采用 `rule_type + file_path + location + normalized evidence` 的 SHA-256，最终规范需结合漏洞规则库确认。
- 报告默认支持 Markdown 和 HTML；PDF 未确认，不进入当前值域。
- `domain_events.sequence` 在领域服务持锁后分配；如果未来单项目事件并发显著增加，应评估独立计数器表，但 MVP 不新增第 17 张表。
- `knowledge_entries.embedding` 向量维度（默认 1536）取决于所选 Embedding 模型，首次 Migration 创建表后由应用层启动校验一致性。
- `knowledge_entries.language` 和 `framework` 使用逗号分隔字符串而非数组，该设计基于 pgvector 与部分 SQLAlchemy ORM 对数组列联合向量查询的兼容性限制，ARM 架构 PostgreSQL 适配时需重新评估。
- `knowledge_retrievals` 作为追加型表，预计每项目每天 < 100 条，无需提前分区；若日检索量超过万级再评估按月分区。
- IVFFlat 向量的 lists 参数在索引创建时确定，后续条目增长需要周期性重建索引以更新 lists，该流程应在运维文档中补充。
- 知识条目自动沉淀（`source_type = 'auto_curated'`）的触发条件和审核流程尚未定义，当前所有自动沉淀条目默认 `entry_status = 'draft'`。
