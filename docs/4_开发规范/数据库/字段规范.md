# 自动化安全评估系统数据库字段规范

## 1. 适用范围

本规范适用于自动化安全评估系统 MVP 的 PostgreSQL DDL、SQLAlchemy 2 Model、Alembic migration、Pydantic Schema、SQL 查询和数据库评审。新增或修改字段时，必须同时更新 `数据库设计.md`、`初始化sql.md`、相关 Model、migration 和测试。

## 2. 表命名规范

- 表名使用复数 `snake_case`，例如 `projects`、`runtime_stages`。
- 关联明细表使用“主实体 + 明细含义”，例如 `attack_path_items`。
- 不使用 `tbl_`、`t_` 等无意义前缀。
- 不使用 PostgreSQL 关键字、缩写歧义或中文表名。
- 表名必须能反映业务实体，不以页面、接口或实现类命名。

正确示例：`project_runtimes`、`resource_usages`。

错误示例：`projectRuntime`、`tbl_log`、`data1`。

## 3. 字段命名规范

- 字段名使用 `snake_case`。
- 主键统一为 `id`。
- 外键使用 `<entity>_id`，例如 `project_id`、`stage_id`。
- 时间点使用 `*_at`，日期使用 `*_date`。
- 数量使用 `*_count`，文件大小使用 `*_bytes`。
- 状态使用 `*_status` 或上下文明确的 `status`。
- 类型使用 `*_type`。
- 有序位置使用 `*_order`；事件序号使用 `sequence`。
- 布尔字段使用 `is_*`、`has_*`、`can_*`。
- 哈希字段带算法，例如 `content_sha256`、`evidence_fingerprint`。
- 计量含义无法从字段名判断时，必须在注释和 API Schema 中明确单位。
- 不使用 `data`、`value`、`info` 等缺少上下文的泛化字段。

## 4. 主键与外键规范

### 4.1 主键

- 对外暴露的业务实体使用 `uuid DEFAULT gen_random_uuid()`。
- 高频追加型内部记录使用 `bigint GENERATED ALWAYS AS IDENTITY`。
- 不允许使用业务编号作为主键；`vuln_code`、`path_code` 和配置 `version` 都是候选键。
- 约束命名为 `pk_<table>`。

本项目 UUID 表：

- `users`
- `projects`
- `project_runtimes`
- `runtime_stages`
- `worker_tasks`
- `vulnerabilities`
- `attack_paths`
- `reports`
- `system_configs`
- `file_artifacts`

本项目 BIGINT IDENTITY 表：

- `attack_path_items`
- `chat_messages`
- `runtime_logs`
- `resource_usages`
- `audit_logs`
- `domain_events`

### 4.2 外键

- 外键类型必须与父表候选键完全一致。
- 单列外键命名为 `fk_<table>__<column>__<ref_table>`。
- 复合外键使用可读范围名，例如 `fk_runtime_logs__worker_scope__worker_tasks`。
- 所有项目子实体必须直接包含 `project_id`。
- 涉及阶段、任务、漏洞、路径、报告和文件的跨表关系，应把 `project_id` 纳入复合外键，禁止只依赖应用层检查同项目。
- 外键索引根据查询和删除路径显式设计，不机械重复唯一约束已有索引。

## 5. 数据类型选择规范

| 业务含义 | PostgreSQL 类型 | 规则 |
| --- | --- | --- |
| 业务标识 | `uuid` | 使用 `gen_random_uuid()` |
| 高频内部游标 | `bigint identity` | 不对外暴露为业务 ID |
| 短标识、状态、类型 | `varchar(n)` | 必须设置合理上限 |
| 不定长正文 | `text` | 不使用无意义的大长度 `varchar` |
| 布尔值 | `boolean` | 不使用 `0/1` 字符串 |
| 整数计数 | `integer` 或 `bigint` | 添加非负或正数 CHECK |
| 精确比例 | `numeric(p,s)` | 不使用浮点存精确值 |
| 时间点 | `timestamptz` | UTC |
| 动态对象 | `jsonb` | 必须检查顶层 JSON 类型 |
| IP 地址 | `inet` | 例如 `audit_logs.client_ip` |
| 字符串集合 | `varchar(n)[]` | 仅用于简单、受控集合 |

不使用 `serial`、`timestamp without time zone`、PostgreSQL 原生 ENUM 或 `money`。

## 6. 字符串长度规范

| 内容 | 推荐上限 | 本项目示例 |
| --- | ---: | --- |
| 用户名、业务编号 | 64 | `username`、`vuln_code`、`path_code` |
| 状态、类型 | 16 至 64 | `risk_level`、`project_status` |
| 名称、标题 | 128 至 255 | `project_name`、`vuln_title` |
| 媒体类型 | 127 | `media_type` |
| 密码哈希 | 255 | `password_hash` |
| 幂等键、外部标识 | 128 | `idempotency_key`、`runtime_identifier` |

所有必填字符串必须通过 `char_length(btrim(column)) > 0` 或更严格规则拒绝空字符串。用户名必须在应用写入前转换为小写，数据库检查规范化结果。

## 7. 大文本与 JSONB 规范

- 任务内容、日志、漏洞证据、报告正文等使用 `text`。
- `jsonb` 仅用于结构随协议演进的对象：
  - `project_runtimes.environment_snapshot`
  - `system_configs.settings`
  - `audit_logs.metadata`
  - `domain_events.payload`
- JSONB 顶层必须是对象，通过 `jsonb_typeof(column) = 'object'` 检查。
- 可稳定查询、排序、关联或约束的数据必须拆为普通字段。
- JSONB 写入前执行字段白名单、大小限制和敏感键过滤。
- 不为完整 JSONB 建普通 B-tree 索引；只有出现明确 JSON 查询后再评估 GIN 或表达式索引。
- 不允许把密码、密钥、Token、Cookie、私有仓库凭证或完整源码塞入 JSONB。

## 8. 时间与时区规范

- 时间点统一使用 `timestamptz`。
- 默认值使用 `CURRENT_TIMESTAMP`。
- 数据库、API、Worker 和测试环境统一使用 UTC。
- API 输出 ISO 8601 并带时区，例如 `2026-07-24T08:30:00Z`。
- 成对时间字段必须检查先后关系，例如 `finished_at >= started_at`。
- `created_at` 表示记录创建时间，`updated_at` 由统一 trigger 维护。
- 采样时间使用 `recorded_at`，事件发生时间使用 `occurred_at`，投递成功使用 `published_at`。
- 不使用本地时间字符串或整数时间戳代替 `timestamptz`。

## 9. 状态与类型字段规范

- 状态和类型使用英文小写 `snake_case` 技术值。
- 数据库使用 `varchar` 与命名 CHECK，不使用 PostgreSQL 原生 ENUM。
- 不同领域使用不同值域，禁止复用一个“通用状态枚举”。
- 修改值域必须通过 Alembic migration、领域模型、Pydantic、前端合同和测试同步变更。
- 项目停止只更新 `projects.project_status` 和 `stop_requested_at`，不得给阶段或任务增加 `stopped`。

本项目权威值域以 `数据库设计.md` 的“状态与类型值域”为准。

## 10. 布尔字段规范

- 布尔字段必须使用 `boolean`，命名为 `is_*`、`has_*` 或 `can_*`。
- 默认值必须明确，避免可空三态，除非业务确实区分未知。
- `system_configs.is_active` 非空，默认 `false`。
- 不使用 `status = 0/1` 表达布尔语义。
- 对“唯一生效”语义使用部分唯一索引，不依赖应用查询后再写入。

## 11. 数值、计数、比例、容量与单位

- 次数、序号和计数添加 `>= 0` 或 `> 0` CHECK。
- `attempt_count`、`retry_count` 为非负整数。
- `stage_order` 固定为 `1` 至 `5`，并与阶段名联合检查。
- `step_order` 从 `1` 连续，由延迟约束触发器校验。
- `size_bytes`、`memory_usage` 使用 `bigint`，单位统一为字节。
- `token_count` 使用 `bigint`，定义为采样时累计 token 数。
- `cpu_usage` 使用 `numeric(9,3)`，定义为容器 CPU 百分值；多核场景允许超过 `100`，但不得小于 `0`。
- 时间长度使用明确单位后缀，例如 `default_timeout_seconds`。
- 保留周期使用 `*_retention_days`。

## 12. 文件路径、逻辑键、哈希和媒体类型

- `projects.source_path` 在 `local` 模式下是管理员授权根目录内相对路径。
- `vulnerabilities.file_path` 是源码根目录内相对路径。
- `workspace_key`、`repository_key`、`report_file_path` 和 `logical_key` 是 `ArtifactStorage` 逻辑键。
- 逻辑键不得以 `/` 开头，不得包含独立 `..` 路径段。
- 路径必须在应用层规范化并校验真实路径仍位于允许根目录，数据库 CHECK 只作第二道防线。
- 文件内容摘要使用小写十六进制 SHA-256。
- 媒体类型使用 IANA 形式，例如 `text/markdown`、`text/html`、`application/json`。
- 文件大小使用 `size_bytes bigint`。
- 用户输入不得直接拼接宿主机路径。

## 13. 密码、凭证与敏感字段

- `users.password_hash` 只保存 Argon2id 哈希，不保存密码、盐的独立明文字段或可逆密文。
- 认证 Cookie、访问令牌、模型 API Key、Git 私钥、仓库密码和证书禁止入库。
- 仓库 URL 写入 `source_path` 前必须移除内联密码和敏感查询参数。
- 审计、日志、事件和环境快照统一经过脱敏器。
- 错误字段只保存可诊断摘要，不保存完整环境变量、请求头或命令敏感参数。
- 数据库注释、测试夹具和 migration 中同样禁止真实密钥。

## 14. 审计字段规范

- 用户操作使用 `actor_user_id`，项目操作使用 `project_id`。
- 请求链路使用 `request_id uuid`。
- 写操作幂等值使用 `idempotency_key varchar(128)`。
- 审计对象使用 `object_type` 与脱敏 `object_id` 快照。
- 审计结果使用 `success`、`failure`、`denied`。
- 项目或用户删除后需要保留审计时，外键使用 `ON DELETE SET NULL`。
- `metadata` 仅保存白名单扩展信息。
- 审计记录是追加型，不提供业务更新接口。

## 15. 默认值与空值规范

- 默认值只能表达稳定业务语义，不得写入未经确认的资源配额或保留周期。
- `projects.project_status` 默认 `created`。
- 阶段和角色任务状态默认 `idle`。
- 漏洞验证状态默认 `pending`。
- Outbox 投递状态默认 `pending`，重试次数默认 `0`。
- 未确认的超时、并发和保留周期保持 `NULL`，不猜测生产值。
- `NULL` 表示未知、尚未发生或不适用；空字符串不能替代 `NULL`。
- JSON 对象默认 `{}`，简单集合可默认空数组。
- `finished_at`、`published_at` 等未发生事件必须为 `NULL`。

## 16. 唯一约束与 CHECK 约束

- 唯一约束命名为 `uq_<table>__<columns>`。
- CHECK 命名为 `ck_<table>__<rule>`。
- 业务编号通常在项目范围唯一，例如：
  - `(project_id, vuln_code)`
  - `(project_id, path_code)`
  - `(project_id, sequence)`
- 可空字段的唯一性使用部分唯一索引，例如 `runtime_identifier`。
- 需要事务内批量重排的唯一约束使用 `DEFERRABLE INITIALLY DEFERRED`。
- CHECK 负责值域、格式、范围、字段间静态关系，不用触发器实现完整业务状态机。
- 跨行约束仅在必要时使用约束触发器，并要求具备事务测试。

## 17. 索引命名与设计规范

- 普通索引命名为 `ix_<table>__<columns>`。
- 唯一索引命名为 `uq_<table>__<columns>`。
- 外键列根据父表删除、关联查询和过滤方式评估索引。
- 列表查询优先使用“租户或项目范围 + 时间 + 游标”组合索引。
- PostgreSQL 索引列顺序按等值过滤、范围过滤、排序顺序排列。
- 低选择性状态字段不单独建索引，应与项目和时间组合。
- 可空稀疏字段使用部分索引。
- 不重复创建已由主键或唯一约束提供的索引。
- 不给大段 `text`、完整 JSONB、密码哈希或敏感字段创建普通索引。
- 新索引必须记录对应 SQL、预期查询和 `EXPLAIN` 验证结果。

## 18. 外键删除策略规范

| 策略 | 使用场景 | 本项目示例 |
| --- | --- | --- |
| `CASCADE` | 从记录没有独立生命周期 | 项目与阶段、日志、漏洞、报告 |
| `RESTRICT` | 父记录不应在仍被使用时删除 | 用户与项目、用户与配置 |
| `NO ACTION` | 保留任务追溯，同时允许项目单语句级联清理 | 任务与漏洞、路径、报告、文件 |
| `SET NULL` | 删除父记录后仍保留历史 | 审计与用户、项目 |

数据库级联只影响数据库记录，不负责删除容器、宿主机文件或对象存储对象。外部资源必须由幂等清理任务先处理。

## 19. SQLAlchemy Model 映射规范

- 使用 SQLAlchemy 2 typed declarative，不使用旧式未类型化 Column 模式。
- Python 字段类型与数据库可空性保持一致。
- 服务器默认使用 `server_default`，不要只写 Python 默认值。
- 约束和索引名称与 DDL 完全一致。
- 关系加载策略必须避免列表接口 N+1 查询。
- 时间对象必须是带时区 `datetime`。

示例：

```python
from datetime import datetime
from uuid import UUID

from sqlalchemy import CheckConstraint, DateTime, ForeignKey, String, text
from sqlalchemy.dialects.postgresql import UUID as PG_UUID
from sqlalchemy.orm import Mapped, mapped_column


class Project(Base):
    __tablename__ = "projects"
    __table_args__ = (
        CheckConstraint(
            "project_status IN "
            "('created', 'running', 'completed', 'failed', 'stopped')",
            name="ck_projects__project_status",
        ),
    )

    id: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True),
        primary_key=True,
        server_default=text("gen_random_uuid()"),
    )
    project_name: Mapped[str] = mapped_column(String(128), nullable=False)
    project_status: Mapped[str] = mapped_column(
        String(32),
        nullable=False,
        server_default=text("'created'"),
    )
    created_by: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True),
        ForeignKey(
            "users.id",
            name="fk_projects__created_by__users",
            ondelete="RESTRICT",
        ),
        nullable=False,
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
        server_default=text("CURRENT_TIMESTAMP"),
    )
```

## 20. Pydantic 与 API 字段映射

- API 使用与数据库一致的 `snake_case` 字段；前端类型从 OpenAPI 生成。
- UUID 使用 `UUID`，时间使用带时区 `datetime`。
- 状态字段使用 Python `StrEnum` 或 `Literal`，值必须与数据库 CHECK 同源。
- 输入 Schema 不暴露数据库管理字段，例如 `id`、`created_at`、`updated_at`。
- 输出日志和列表 Schema 必须字段裁剪，不返回大文本正文。
- `password_hash` 永不出现在响应 Schema。
- `source_path`、日志、证据和事件载荷在响应前再次脱敏。
- `memory_usage` 的 API 描述明确单位为字节，`cpu_usage` 明确为百分值。

示例：

```python
from datetime import datetime
from enum import StrEnum
from uuid import UUID

from pydantic import BaseModel, ConfigDict


class ProjectStatus(StrEnum):
    CREATED = "created"
    RUNNING = "running"
    COMPLETED = "completed"
    FAILED = "failed"
    STOPPED = "stopped"


class ProjectSummary(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: UUID
    project_name: str
    project_status: ProjectStatus
    created_at: datetime
    updated_at: datetime
```

## 21. PostgreSQL DDL 示例

```sql
CREATE TABLE example_records (
    id uuid DEFAULT gen_random_uuid() NOT NULL,
    project_id uuid NOT NULL,
    record_status varchar(32) DEFAULT 'pending' NOT NULL,
    size_bytes bigint NOT NULL,
    created_at timestamptz DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at timestamptz DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT pk_example_records PRIMARY KEY (id),
    CONSTRAINT fk_example_records__project_id__projects
        FOREIGN KEY (project_id)
        REFERENCES projects (id)
        ON DELETE CASCADE,
    CONSTRAINT ck_example_records__record_status
        CHECK (record_status IN ('pending', 'ready', 'failed')),
    CONSTRAINT ck_example_records__size_bytes
        CHECK (size_bytes >= 0)
);

CREATE INDEX ix_example_records__project_id_created_at
    ON example_records (project_id, created_at DESC);
```

示例仅说明字段和约束写法，不表示本项目新增 `example_records` 表。

## 22. 正确示例与反例

| 场景 | 正确 | 反例 | 原因 |
| --- | --- | --- | --- |
| 时间 | `created_at timestamptz` | `create_time varchar(20)` | 保留时区和类型语义 |
| 文件大小 | `size_bytes bigint` | `file_size varchar(32)` | 类型和单位明确 |
| 状态 | `project_status` + CHECK | `status integer` | 避免魔法数字 |
| 外键 | `(stage_id, project_id)` 复合 FK | 只校验 `stage_id` | 防止跨项目关联 |
| 文件路径 | `reports/{project_id}/report.md` | `/var/data/report.md` | 保存逻辑键而非绝对路径 |
| 密码 | Argon2id `password_hash` | `password` | 禁止明文和可逆存储 |
| JSONB | 动态事件 `payload` | 把项目全部字段放 `data` | 稳定字段应结构化 |
| 计数 | `retry_count >= 0` | 无约束整数 | 防止无效负值 |
| 索引 | `(project_id, created_at DESC)` | 只索引 `status` | 匹配真实查询 |
| 空值 | 未完成的 `finished_at = NULL` | 空字符串 | 保持类型和语义 |

## 23. 数据库评审检查清单

- 表名和字段名是否为正确的复数及 `snake_case`。
- 主键类型是否符合业务实体或高频追加表策略。
- 原始需求字段是否保留，重命名是否有映射。
- 外键类型、候选键和删除策略是否一致。
- 是否通过复合外键阻止跨项目关联。
- 状态值是否与项目、阶段、任务等领域分别定义。
- 时间字段是否全部使用 `timestamptz` 和 UTC。
- 数值是否明确单位并设置范围约束。
- 必填字符串是否拒绝空字符串。
- 文件键和源码路径是否阻止绝对路径及路径穿越。
- JSONB 是否必要、限长、脱敏并检查顶层类型。
- 是否保存了密码明文、凭证、Token、Cookie 或证书。
- 唯一约束、CHECK、外键和索引是否具有规范名称。
- 索引是否对应真实过滤、排序和分页查询。
- 是否重复创建主键或唯一约束已有索引。
- `runtime_logs`、`resource_usages` 是否支持项目与时间范围查询。
- Outbox 事件是否与业务变更同事务写入。
- `event_id` 和项目内 `sequence` 是否都能去重。
- 攻击路径是否至少一步、顺序连续且漏洞同项目。

- 外部文件和容器清理是否与数据库级联边界清楚。
