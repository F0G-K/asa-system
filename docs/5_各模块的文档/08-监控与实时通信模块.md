# 监控与实时通信模块（monitoring）

## 1. 模块概述

### 1.1 定位

`monitoring` 模块负责项目运行期间的过程数据采集、存储和推送——包括角色协作消息、结构化运行日志、CPU/内存/Token 资源采样，以及通过 Outbox + Event Relay + WebSocket 实现的实时事件推送。

### 1.2 设计依据

- `docs/1_PRD/自动化安全评估系统-PRD.md`
- `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md` — 第 5.2 节、第 8.4 节
- `docs/4_开发规范/API接口文档.md` — 第 6 章（过程监控接口）、第 8 章（WebSocket 实时接口）
- `docs/4_开发规范/后端/后端开发规范.md` — 第 14 章（实时事件与 WebSocket）
- `docs/4_开发规范/数据库/数据库设计.md` — `chat_messages`、`runtime_logs`、`resource_usages`、`domain_events` 表设计

### 1.3 职责边界

| 子模块 | 职责 |
| --- | --- |
| 消息管理 | 保存角色协作消息，支持按阶段/角色/时间回放 |
| 日志管理 | 保存脱敏结构化运行日志，支持按级别/阶段/任务/时间查询 |
| 资源采样 | 保存 CPU、内存、Token 累计采样，支持时间序列查询 |
| Event Relay | 从 `domain_events` 批量领取事件，发布到 Redis Stream |
| WebSocket | 握手认证、事件推送、心跳、续传、慢客户端断开 |

**不负责：** 阶段和任务状态变更（scheduler）、漏洞发现推送内容生成（agents）、报告状态推送内容（reports）——推送的**内容**由对应模块生成，monitoring 只负责**传输**。

## 2. 架构与依赖

### 2.1 数据流全景

```text
业务事务 (Worker/API)
  │
  ├── 1. 写业务表 + domain_events (同事务)
  │
  └── 提交

Event Relay (apps/worker/event_relay/)
  │
  ├── 2. FOR UPDATE SKIP LOCKED 批量领取 pending 事件
  ├── 3. 发布到 Redis Stream: project:{project_id}:events
  └── 4. 标记 domain_events.publish_status='published'

WebSocket 服务 (apps/api/websocket/)
  │
  ├── 5. 读取 Redis Stream，从 after_sequence 续传
  ├── 6. 推送 JSON 事件到浏览器
  └── 7. 浏览器按 event_id 去重，更新 UI

REST 补偿（断线重连时）：
  浏览器 → GET /api/v1/projects/{id}/stages|workers|messages|logs|resources
```

### 2.2 涉及的数据库表

| 表 | 角色 | 写入特征 |
| --- | --- | --- |
| `chat_messages` | 角色协作消息 | 追加型、BIGINT 游标 |
| `runtime_logs` | 结构化运行日志 | 高频追加型、BIGINT 游标 |
| `resource_usages` | 资源采样 | 固定周期追加型、BIGINT 游标 |
| `domain_events` | Outbox 事件 | 业务事务内追加 |

### 2.3 涉及的 API 接口

| 接口 | 方法 | URL | 说明 |
| --- | --- | --- | --- |
| 查询角色消息 | `GET` | `/api/v1/projects/{project_id}/messages` | 游标分页，支持多维度筛选 |
| 查询运行日志 | `GET` | `/api/v1/projects/{project_id}/logs` | 游标分页，支持级别/时间/阶段/任务筛选 |
| 查询资源消耗 | `GET` | `/api/v1/projects/{project_id}/resources` | 游标分页，时间序列 |
| 订阅实时事件 | `WS` | `/api/v1/projects/{project_id}/stream` | WebSocket |

## 3. 消息管理

### 3.1 消息实体

```text
ChatMessage
├── id: bigint                        # 游标
├── project_id: UUID                  # 所属项目
├── stage_id: UUID?                   # 可选阶段
├── worker_task_id: UUID?             # 可选角色任务
├── worker_role: str?                 # 可选发送角色
├── message_type: str                 # 消息协议类型（闭集待定）
├── message_text: str                 # 脱敏消息正文
└── created_at: datetime
```

### 3.2 查询实现

```text
GET /api/v1/projects/{project_id}/messages
  ?cursor=1842&limit=100
  &stage_id=xxx&worker_role=code_analyst
  &start_at=...&end_at=...

查询条件：
  ├── WHERE project_id = :pid
  ├── AND id > :cursor (游标分页)
  ├── AND stage_id = :sid (可选)
  ├── AND worker_role = :role (可选)
  ├── AND message_type = :type (可选)
  ├── AND created_at >= :start_at (可选)
  └── AND created_at < :end_at (可选)

排序：ORDER BY (created_at, id) ASC  ← 便于前端追加展示
索引：ix_chat_messages__project_id_created_at

返回：
  { items: [...], next_cursor: 1842, has_more: false }
```

## 4. 日志管理

### 4.1 日志实体

```text
RuntimeLog
├── id: bigint                        # 游标
├── project_id: UUID
├── stage_id: UUID?                   # 可选阶段
├── worker_task_id: UUID?             # 可选角色任务
├── request_id: UUID?                 # 请求链路
├── log_level: "debug" | "info" | "warning" | "error"
├── log_content: str                  # 脱敏日志正文
└── created_at: datetime
```

### 4.2 日志规则

- 日志在进入数据库前脱敏：去除密码、Token、Cookie、密钥、证书、仓库凭证和宿主机敏感路径。
- `log_content` 长度受控（上限由配置决定，超出截断并标注）。
- 高频运行日志批量提交（如每 50 条或每 5 秒），避免每行独立事务。
- 大范围查询同时受服务端最大时间窗口和 `limit` 限制。

### 4.3 查询实现

```text
GET /api/v1/projects/{project_id}/logs
  ?cursor=90215&limit=100
  &start_at=...&end_at=...
  &log_level=warning&log_level=error
  &stage_id=xxx&worker_task_id=xxx
  &request_id=xxx&order=desc

查询条件：
  ├── WHERE project_id = :pid
  ├── AND log_level = ANY(:levels) (可选)
  ├── AND stage_id / worker_task_id / request_id (可选)
  └── 时间窗口限制（服务端强制最大跨度）

排序：默认 (created_at, id) ASC；支持 DESC
索引：
  ├── ix_runtime_logs__project_id_created_at
  ├── ix_runtime_logs__stage_id_created_at
  ├── ix_runtime_logs__worker_task_id_created_at
  └── ix_runtime_logs__request_id
```

## 5. 资源采样

### 5.1 资源采样实体

```text
ResourceUsage
├── id: bigint                        # 游标
├── project_id: UUID
├── runtime_id: UUID                  # 运行实例
├── cpu_usage: numeric(9,3)           # CPU 百分值，可超过 100
├── memory_usage: bigint              # 字节
├── token_count: bigint               # 累计 token
└── recorded_at: datetime
```

### 5.2 查询实现

```text
GET /api/v1/projects/{project_id}/resources
  ?cursor=33105&limit=300
  &start_at=...&end_at=...

返回：
  {
    items: [{ id, runtime_id, cpu_usage, memory_usage, token_count, recorded_at }],
    next_cursor: 33105,
    has_more: true,
    units: {
      cpu_usage: "percent",
      memory_usage: "bytes",
      token_count: "count"
    }
  }

排序：默认 (recorded_at, id) ASC
前端按时间顺序绘图；较大查询窗口由服务端降采样。
```

## 6. Event Relay

### 6.1 设计原则

- Event Relay 是独立进程（部署在 `apps/worker/` 中但使用独立命令入口）。
- 它只做：读取 → 发布 → 标记完成。不修改项目、阶段、任务状态。
- 发布失败不回滚数据库事务（Outbox 模式的核心属性）。

### 6.2 工作流程

```text
Event Relay 主循环：
  │
  ├── 1. SELECT * FROM domain_events
  │     WHERE publish_status = 'pending'
  │        OR (publish_status = 'failed' AND next_retry_at <= NOW())
  │     ORDER BY id
  │     LIMIT 100
  │     FOR UPDATE SKIP LOCKED
  │
  ├── 2. 逐个处理：
  │     │
  │     ├── 发布到 Redis Stream: XADD project:{project_id}:events * ...
  │     │     消息体包含：event_id, sequence, event_type, project_id, occurred_at, data
  │     │
  │     ├── 发布成功：
  │     │     UPDATE domain_events
  │     │     SET publish_status = 'published', published_at = NOW()
  │     │     WHERE id = :id
  │     │
  │     └── 发布失败：
  │           UPDATE domain_events
  │           SET publish_status = 'failed',
  │               retry_count = retry_count + 1,
  │               next_retry_at = NOW() + backoff(retry_count),
  │               last_error = :error
  │           WHERE id = :id
  │
  └── 3. 间隔等待，继续下一批
```

### 6.3 事件类型

| `event_type` | `data` 必含字段 | 来源 |
| --- | --- | --- |
| `project_status` | `project_status`、`stop_requested_at` | projects |
| `stage_status` | `stage_id`、`stage_name`、`stage_status` | scheduling |
| `worker_status` | `worker_task_id`、`worker_role`、`task_status` | scheduling |
| `chat_message` | `message_id`、`worker_role`、`message_type`、`message_text` | monitoring |
| `runtime_log` | `log_id`、`log_level`、`log_content` | monitoring |
| `resource_usage` | `resource_usage_id`、`cpu_usage`、`memory_usage`、`token_count` | monitoring |
| `vulnerability_found` | `vulnerability_id`、`vuln_code`、`vuln_title`、`risk_level` | vulnerabilities |
| `report_ready` | `report_id`、`version`、`report_status` | reports |

## 7. WebSocket 实时推送

### 7.1 握手指南

```text
WS /api/v1/projects/{project_id}/stream?after_sequence=1024
  │
  ├── 握手校验：
  │     ├── Cookie: asa_session 有效且未过期
  │     ├── Origin 校验
  │     ├── project_id 为有效 UUID
  │     ├── 用户有项目访问权限
  │     └── Sec-WebSocket-Protocol: asa.v1 (可选)
  │
  ├── 握手成功 → 101 Switching Protocols
  └── 握手失败 → 按接口文档返回 401/403/404/422

拒绝场景：
  ├── 401 AUTH_REQUIRED          — 未登录或会话过期
  ├── 403 PROJECT_ACCESS_DENIED  — 无项目权限
  ├── 404 PROJECT_NOT_FOUND      — 项目不存在
  └── 422 VALIDATION_ERROR       — UUID 或序号无效
```

### 7.2 推送事件格式

```json
{
  "event_id": "e61adea9-...",
  "sequence": 1024,
  "event_type": "stage_status",
  "project_id": "a8c3f3e0-...",
  "occurred_at": "2026-07-24T09:02:19Z",
  "data": {
    "stage_id": "179a46a8-...",
    "stage_name": "code_analysis",
    "stage_status": "running"
  }
}
```

每个连接只订阅一个项目。服务端按 `sequence` 顺序发送。

### 7.3 续传与补偿

```text
after_sequence 续传：
  ├── 指定 after_sequence=1024
  │     └── 从 Redis Stream 中 sequence > 1024 的事件开始推送
  ├── Stream 仍保留窗口内 → 正常续传
  └── 超出保留窗口 → 4009 EVENT_GAP_TOO_LARGE 关闭
        └── 客户端应调用 REST 接口全量补偿：
              GET projects/{id} → 项目状态
              GET projects/{id}/stages → 阶段状态
              GET projects/{id}/workers → 角色任务
              GET projects/{id}/messages → 最新消息
              GET projects/{id}/logs → 最新日志
              GET projects/{id}/resources → 最新资源
              GET projects/{id}/vulnerabilities → 漏洞
              GET projects/{id}/attack-paths → 攻击路径
              然后以最新 sequence 重连
```

### 7.4 心跳与会话管理

```text
客户端 → 服务端（每 30 秒）:
  { "type": "ping", "sent_at": "2026-07-24T09:06:30Z" }

服务端 → 客户端:
  { "type": "pong", "server_time": "2026-07-24T09:06:30Z" }

超时策略（由容量测试确定具体值）：
  ├── 空闲超时：如 120 秒无消息 → 关闭连接 (1001)
  ├── 会话过期：会话在连接期间失效 → 4001 SESSION_EXPIRED 关闭
  ├── 权限撤销：权限被撤销 → 4003 PROJECT_ACCESS_DENIED 关闭
  ├── 慢客户端：发送缓冲超过上限 → 4010 CLIENT_TOO_SLOW 关闭
  └── 重连限流：过于频繁重连 → 4008 RATE_LIMITED 关闭
```

### 7.5 关闭码

| 关闭码 | 业务含义 | 客户端行为 |
| ---: | --- | --- |
| 1001 | 空闲超时 | 正常重连 |
| 4001 | `SESSION_EXPIRED` | 引导重新登录 |
| 4003 | `PROJECT_ACCESS_DENIED` | 停止重连 |
| 4008 | `RATE_LIMITED` | 退避后重连 |
| 4009 | `EVENT_GAP_TOO_LARGE` | REST 全量补偿后重连 |
| 4010 | `CLIENT_TOO_SLOW` | 检查消费能力后重连 |
| 1011 | `INTERNAL_ERROR` | 退避后重连 |

## 8. 代码实现指南

### 8.1 目录结构

```text
packages/backend-core/src/asa_core/domain/monitoring/
├── entities.py              # ChatMessage, RuntimeLog, ResourceUsage, DomainEvent
└── value_objects.py         # LogLevel, MessageType

packages/backend-core/src/asa_core/application/
├── queries/
│   ├── list_messages.py     # ListMessages
│   ├── list_logs.py         # ListLogs
│   └── list_resources.py    # ListResources
└── ports/
    ├── message_repository.py
    ├── log_repository.py
    └── resource_repository.py

apps/api/src/asa_api/
├── routers/v1/monitoring.py       # messages, logs, resources 路由
├── schemas/monitoring.py          # 请求/响应 Schema
└── websocket/
    ├── handler.py                 # WebSocket 握手和生命周期
    ├── session.py                 # 连接会话管理
    ├── publisher.py               # 从 Redis Stream 读取并推送
    └── heartbeat.py               # 心跳和超时管理

apps/worker/src/asa_worker/event_relay/
├── relay.py                  # 主循环：领取 → 发布 → 标记
└── backoff.py                # 重试退避策略
```

### 8.2 关键实现约束

- **日志和资源批量写入**：高频数据不逐条独立事务，使用有上限的批量 INSERT。
- **游标分页**：消息、日志和资源使用 `(created_at, id)` 稳定游标，不使用 `OFFSET` 扫描大表。
- **游标不跨项目复用**：游标绑定当前查询条件，防止通过修改参数跨越权限。
- **服务端强制查询上限**：时间窗口和 `limit` 均有最大值，不接受无边界查询。
- **Event Relay 不修改业务状态**：只读取 `domain_events`、发布到 Redis、标记投递状态。
- **WebSocket 与业务事务解耦**：Redis 或 WebSocket 失败不得回滚已提交的数据库业务事务。
- **event_id 去重**：消费者（WebSocket 服务端和浏览器）均按 `event_id` 去重。
- **日志高峰合并**：资源采样事件允许合并，但状态、漏洞和报告事件语义不得改变。

## 9. 安全要点

- WebSocket 握手必须校验 `asa_session` Cookie、Origin、项目 UUID 和项目权限。
- 消息、日志和资源查询必须附加项目权限条件（`projects.created_by`）。
- 日志和消息进入响应前再次脱敏（防范存储时遗漏的敏感信息）。
- WebSocket 单连接只订阅一个项目，不接受客户端任意切换 Stream。
- WebSocket 连接数按用户/IP限流，防止连接耗尽。
- `log_content` 和 `message_text` 前端展示时执行安全转义。

## 10. 测试要点

### 10.1 API 测试

- `GET /api/v1/projects/{project_id}/messages` — 游标分页、多维度筛选、时间范围校验
- `GET /api/v1/projects/{project_id}/logs` — 游标分页、日志级别筛选、order=desc、时间窗口限制
- `GET /api/v1/projects/{project_id}/resources` — 时间序列、units 字段、降采样
- 未登录（401）、无权限（403/404）

### 10.2 WebSocket 测试

- 握手成功（101）、握手失败（401/403/404/422）
- 事件按 sequence 顺序推送
- `after_sequence` 续传（窗口内）
- `after_sequence` 超出窗口（4009 关闭）
- 心跳 ping/pong
- 空闲超时断开
- 慢客户端断开（4010）
- 会话过期断开（4001）
- 浏览器端 event_id 去重

### 10.3 Event Relay 测试

- 批量领取 pending 事件
- 发布成功标记 published
- 发布失败更新 retry_count 和 next_retry_at
- 重复投递时消费者去重
- Event Relay 崩溃重启后从 last_error 恢复
