  ## 三、数据库技术基线

  数据库使用 PostgreSQL，ORM 使用 SQLAlchemy 2，迁移工具使用 Alembic。

  设计必须符合以下原则：

  - PostgreSQL 是业务权威数据源。
  - Redis、WebSocket 和进程内状态不是业务事实源。
  - 所有时间使用 `timestamptz`，按 UTC 写入。
  - 长耗时任务异步执行。
  - 状态变更和 `domain_events` 事件写入必须位于同一事务。
  - 使用事务性 Outbox 模式，由 `event-relay` 投递事件。
  - 禁止保存明文密码、认证 Cookie、私有仓库密钥、token 或证书。
  - 文件字段保存逻辑路径或对象键，不保存用户可控的宿主机绝对路径。
  - MVP 不支持项目在 `completed`、`failed`、`stopped` 后原地重跑。
  - 不要为了“未来可能需要”无依据地增加大量表。
  - 不使用 PostgreSQL 原生 ENUM；状态和类型字段使用 `varchar` 配合 `CHECK` 约束，便于 Alembic 演进。
  - 不为所有表机械增加软删除字段。项目删除按需求执行关联数据清理，审计记录按要求保留必要元数据。
  - `updated_at` 使用统一 PostgreSQL trigger 自动维护，并在设计文档中说明。
  - 初始化 SQL 面向全新数据库，要求事务化、失败即回滚；不要使用大量 `IF NOT EXISTS` 掩盖结构不一致。
  - 除 `CREATE EXTENSION IF NOT EXISTS` 外，DDL 应采用明确、可验证的创建方式。
  - 初始化 SQL 中不得包含 `DROP DATABASE`、`DROP SCHEMA`、`DROP TABLE` 等破坏性语句。

  ## 五、核心业务约束

  数据库设计至少落实以下关系和约束：

  - 一个用户可以创建多个项目。
  - 一个项目只能有一个创建者。
  - 普通用户默认只能访问自己创建或被授权的项目；当前文档未定义授权表时，不得擅自创建复杂授权模型，应列为待确认项。
  - 项目状态：
    - `created`
    - `running`
    - `completed`
    - `failed`
    - `stopped`
  - 阶段名称：
    - `environment_scan`
    - `code_analysis`
    - `vulnerability_verify`
    - `report_generate`
    - `done`
  - 阶段和角色任务状态：
    - `idle`
    - `running`
    - `success`
    - `failed`
  - 六类执行角色：
    - `general`
    - `environment_inspector`
    - `code_analyst`
    - `vulnerability_verifier`
    - `report_editor`
    - `operations_assistant`
  - 漏洞风险等级：
    - `critical`
    - `high`
    - `medium`
    - `low`
    - `info`
  - 漏洞验证状态：
    - `pending`
    - `verified`
    - `rejected`
  - 源码类型：
    - `local`
    - `repository`
  - 日志等级：
    - `debug`
    - `info`
    - `warning`
    - `error`
  - 一个项目可以有多个阶段记录、角色任务、漏洞、攻击路径、消息、日志、资源记录、文件制品和报告记录。
  - 一个阶段可以分发多个角色任务。
  - `attack_path_items` 负责关联攻击路径和漏洞，并通过 `step_order` 保证顺序连续、稳定。
  - 同一个攻击路径只能关联同项目的漏洞。
  - `runtime_logs` 可以关联项目，并可选关联阶段和角色任务。
  - `domain_events` 中：
    - `event_id` 全局唯一；
    - `sequence` 在项目内唯一并保持递增；
    - 记录事件类型、载荷、发生时间、投递状态、重试次数和投递时间。
  - `file_artifacts` 保存逻辑键、文件类型、内容摘要、文件大小、媒体类型和项目归属。
  - `audit_logs` 在项目删除后仍需保留必要的操作元数据，但不得保留被删除项目的敏感内容。
  - 项目删除时，项目业务数据应按明确的 `ON DELETE` 策略清理；外部文件和容器由幂等清理任务处理，不能假设数据库外键可以删除物理文件。
  - 不得只依赖应用层保证“阶段、任务、漏洞、攻击路径属于同一项目”。能通过复合唯一约束和复合外键落实的，应在数据库层落实。
  - `vulnerabilities` 至少保证项目内 `vuln_code` 唯一，并设计合理的漏洞去重指纹约束。
  - `attack_paths` 至少保证项目内 `path_code` 唯一。
  - `attack_path_items` 至少保证 `(path_id, step_order)` 唯一。
  - `runtime_logs`、`resource_usages` 必须具有适合“项目 + 时间范围”查询的组合索引。
  - `domain_events` 必须具有适合待投递事件扫描的索引。
  - 所有计数、序号、文件大小、CPU、内存、token 等字段必须有非负约束或合理取值范围。
  - 大文本使用 `text`；动态事件载荷、配置快照等确有必要的结构化动态数据使用 `jsonb`，禁止滥用 `jsonb` 代替明确字段。
  - 未确认的资源配额、保留天数、并发数、模型名称、容器镜像等不得写死为臆测值。

  ## 六、主键与索引策略

  选择一套明确、一致的主键策略并在四份文档中保持一致。

  推荐策略：

  - 对外暴露的核心业务实体使用 UUID。
  - 高频追加型内部记录可使用 `bigint GENERATED ALWAYS AS IDENTITY`。
  - `domain_events.event_id` 使用 UUID，项目内事件序号使用 `bigint`。
  - 如使用 `gen_random_uuid()`，在初始化 SQL 中声明所需扩展。
  - 所有外键列必须建立必要索引，但不得重复创建已被唯一约束覆盖的索引。
  - 不要给低选择性的状态字段单独建立无效索引；应结合实际查询条件设计组合索引或部分索引。
  - 不得为大段 `text`、完整 JSON 或敏感字段创建普通 B-tree 索引。

  ## 八、设计中特别注意

  1. 不要将项目状态、阶段状态和角色任务状态混为一套枚举。
  2. 项目停止通过项目级取消标记表达，不要擅自给阶段或任务增加与 PRD 冲突的 `stopped` 状态。
  3. 状态流转规则主要由领域服务在事务中控制；数据库负责值域、唯一性和引用完整性，不要尝试用复杂触发器实现完整业务状态机。
  4. `audit_logs` 的项目关联需要兼顾项目删除后的审计保留，可使用可空外键、`ON DELETE SET NULL` 和脱敏对象标识。
  5. `domain_events` 必须支持重复投递去重和按项目断线续传。
  6. 报告内容、报告文件、漏洞证据和文件制品之间的边界必须清楚。
  7. 数据库中的文件路径必须是逻辑键或项目内相对路径，不能作为无需校验即可访问的宿主机路径。
  8. 私有仓库凭证不得保存到 `projects`、日志、审计载荷、事件载荷或报告。
  9. `attack_path_items` 的同项目约束不能只写一句“由应用保证”，应尽量通过数据库复合约束实现。
  10. 对 `runtime_logs`、`resource_usages`、`domain_events`、`audit_logs` 等增长型表说明保留、归档或分区演进策略；MVP 不必过早分区，但要说明触发分区的条件。
  11. 不要引入 Kafka、Elasticsearch、Kubernetes 或额外数据库。
  12. 不要生成与文档无关的 SaaS、多租户、工单、复测或第三方平台表。
