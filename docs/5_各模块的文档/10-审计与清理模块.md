# 审计与清理模块（audit + cleanup）

## 1. 模块概述

### 1.1 定位

`audit` 模块负责记录系统中关键操作的安全审计日志——谁在什么时间对什么资源做了什么操作、结果如何。`cleanup` 模块负责项目删除时的资源协同清理——确保容器销毁、文件删除和数据库记录级联清理的一致性和可恢复性。

两个模块在项目删除流程中密切协作：`cleanup` 执行清理操作，`audit` 记录清理过程和结果。

### 1.2 设计依据

- `docs/1_PRD/自动化安全评估系统-PRD.md`
- `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md` — 第 5.2 节、第 8.7 节
- `docs/4_开发规范/后端/后端开发规范.md` — 第 8.5 节（审计）、第 13.6 节（删除与清理）
- `docs/4_开发规范/数据库/数据库设计.md` — `audit_logs` 表设计

### 1.3 职责边界

**audit 职责：**

| 职责 | 说明 |
| --- | --- |
| 操作审计 | 记录初始化、登录、越权、启动、停止、删除、配置更新等关键操作 |
| 脱敏存储 | 审计元数据使用白名单字段，不保存密码、Cookie、密钥和源码 |
| 持久保留 | 项目/用户删除后通过 `SET NULL` 保留最小审计上下文 |
| 链路关联 | 通过 `request_id` 关联操作链路 |

**cleanup 职责：**

| 职责 | 说明 |
| --- | --- |
| 项目删除协同 | 按顺序销毁容器 → 清理文件 → 删除数据库记录 |
| 幂等重试 | 同一幂等键的清理任务可安全重复执行 |
| 部分失败处理 | 部分步骤失败不得删除项目行，记录失败项供管理员诊断 |
| 定时清理 | 按配置的保留天数清理过期日志和文件 |

### 2.2 审计模块涉及的 API

审计模块不直接暴露独立的 REST API。审计记录在以下操作中由应用层自动写入：

- `POST /api/v1/system/init` → `action='system_init'`
- `POST /api/v1/system/login` → `action='login'`
- `POST /api/v1/system/logout` → `action='logout'`
- `POST /api/v1/projects` → `action='project_create'`
- `POST /api/v1/projects/{id}/start` → `action='project_start'`
- `POST /api/v1/projects/{id}/stop` → `action='project_stop'`
- `DELETE /api/v1/projects/{id}` → `action='project_delete'`
- `PUT /api/v1/system/config` → `action='config_update'`

## 3. 审计模型

### 3.1 审计实体

```text
AuditLog
├── id: bigint                          # 内部游标
├── actor_user_id: UUID?                # 操作者（SET NULL on user delete）
├── project_id: UUID?                   # 关联项目（SET NULL on project delete）
├── request_id: UUID                    # 请求链路标识
├── action: str                         # 操作标识，如 "project_start"
├── object_type: str                    # 对象类型，如 "project"
├── object_id: str?                     # 脱敏对象标识快照
├── result_status: "success" | "failure" | "denied"
├── client_ip: inet?                    # 客户端 IP
├── idempotency_key: str?               # 写操作幂等键
├── metadata: dict                      # 脱敏扩展信息（JSON 对象）
├── created_at: datetime
```

### 3.2 审计事件清单

| action | object_type | 触发时机 | result_status |
| --- | --- | --- | --- |
| `system_init` | `system` | 初始化成功 | `success` |
| `login` | `user` | 登录成功 | `success` |
| `login` | `user` | 密码错误 | `failure` |
| `login` | `user` | 账户禁用 | `denied` |
| `login_rate_limited` | `system` | 登录触发限流 | `denied` |
| `logout` | `session` | 退出 | `success` |
| `access_denied` | `project`/`config` | 越权访问 | `denied` |
| `project_create` | `project` | 创建项目 | `success` |
| `project_start` | `project` | 启动受理 | `success` |
| `project_start` | `project` | 状态冲突拒绝 | `denied` |
| `project_stop` | `project` | 停止受理 | `success` |
| `project_delete` | `project` | 删除受理 | `success` |
| `project_delete` | `project` | 运行中拒绝 | `denied` |
| `config_update` | `system_config` | 配置更新 | `success` |
| `config_update` | `system_config` | 版本冲突 | `failure` |
| `report_download` | `report` | 下载成功 | `success` |
| `report_integrity_error` | `report` | 文件摘要不匹配 | `failure` |

### 3.3 审计脱敏规则

| 写入前处理 | 说明 |
| --- | --- |
| 不写入密码、密码哈希 | 任何操作 |
| 不写入完整 Cookie | 认证相关 |
| 不写入请求体原文 | 登录、初始化 |
| 不写入模型密钥 | AI 调用 |
| 不写入完整源码路径 | 命令执行 |
| object_id 快照 | 保留资源标识（如项目 UUID）但不超过 128 字符 |
| metadata 白名单 | 仅保存 `reason`、`version`、`environment_type` 等已知安全字段 |

### 3.4 数据保留

- 审计记录是**追加型**数据，不提供更新或删除接口。
- 用户或项目删除时外键使用 `ON DELETE SET NULL`，`object_type` 和 `object_id` 保留最小操作上下文。
- 审计数据的保留周期独立于业务数据（建议 >= 日志保留天数）。

## 4. 清理模型

### 4.1 项目删除流程

```text
项目删除（Celery 清理任务，按顺序执行）：

Phase 1: 前置检查
  ├── 校验项目 project_status != 'running'
  ├── 校验 confirm_project_name
  └── 记录清理审计

Phase 2: 容器销毁
  ├── 查询 project_runtimes WHERE project_id = :pid
  ├── 如 container_status 为 running/starting/stopping:
  │     └── 调用 Executor.destroy_container(runtime_id)
  │            ├── 先 SIGTERM，宽限期后 SIGKILL
  │            └── 删除容器及相关网络/卷
  └── 更新 project_runtimes.container_status = 'destroyed'

Phase 3: 文件清理
  ├── 读取 file_artifacts WHERE project_id = :pid
  ├── 按 logical_key 逐个清理物理文件：
  │     ├── reports/{project_id}/
  │     ├── runtime_logs/{project_id}/
  │     ├── workspace/{project_id}/
  │     └── repositories/{project_id}/
  └── 删除成功 → 删除 file_artifacts 记录

Phase 4: 数据库清理
  ├── 确认 Phase 2 和 Phase 3 全部成功
  ├── DELETE FROM projects WHERE id = :pid
  │     └── 外键级联清理：
  │           ├── project_runtimes CASCADE
  │           ├── runtime_stages CASCADE
  │           ├── worker_tasks CASCADE
  │           ├── vulnerabilities CASCADE
  │           ├── attack_paths CASCADE → attack_path_items CASCADE
  │           ├── reports CASCADE → file_artifacts CASCADE
  │           ├── chat_messages CASCADE
  │           ├── runtime_logs CASCADE
  │           ├── resource_usages CASCADE
  │           └── domain_events CASCADE
  ├── audit_logs.project_id → SET NULL (保留审计)
  └── 记录清理完成审计
```

### 4.2 部分失败处理

```text
清理失败场景：
  ├── 容器销毁失败：
  │     └── 记录 error: "container_destroy_failed: {error}"
  │     └── 不删除项目行
  │     └── 允许同幂等键重试（跳过已成功的步骤）
  │
  ├── 部分文件清理失败：
  │     └── 记录 failed_files: [{logical_key, error}]
  │     └── 不删除项目行
  │     └── 允许同幂等键重试
  │
  └── 全部外部资源成功但有文件清理失败：
        └── 项目行保留，记录失败项
        └── 管理员通过日志/监控发现并处理

禁止行为：
  ✗ 部分清理失败时删除项目行（数据不一致）
  ✗ 返回虚假成功
  ✗ 跳过失败项不做记录
```

### 4.3 定时清理

```text
定时清理任务（按 system_configs 中配置的保留天数）：
  ├── 过期日志清理：
  │     DELETE FROM runtime_logs
  │     WHERE created_at < NOW() - INTERVAL ':log_retention_days days'
  │     分批删除（LIMIT 10000），避免长事务
  │
  ├── 过期资源数据清理：
  │     同上逻辑
  │
  └── 过期文件清理：
        读取 file_artifacts WHERE created_at < cutoff
        按 logical_key 清理物理文件
        删除清理成功的 file_artifacts 记录

注意：保留天数为 NULL（未确认）时不自动清理。
```

### 5.2 关键实现约束

**审计：**
- 审计写入失败时，安全敏感写操作（启动、停止、删除、配置更新）不得静默成功。
- `metadata` 只保存白名单字段，不保存完整请求体、Cookie、密码和密钥。
- 审计记录不可修改（追加型数据，业务代码不提供 UPDATE 接口）。
- 审计脱敏是**递归**的——JSON 嵌套结构中也需要过滤敏感键。
- 需要审计但无用户上下文时（如系统初始化），`actor_user_id` 为 NULL，`client_ip` 记录请求来源。

**清理：**
- 清理步骤严格按顺序：先外部资源（容器、文件），再数据库记录。
- **只有全部外部资源成功后**才删除 `projects` 行。
- 数据库外键级联只处理业务记录；容器和物理文件必须由清理任务显式处理。
- 清理任务必须是**幂等**的——同一 `idempotency_key` 可安全重入，跳过已成功的步骤。
- 部分失败时保留失败项详情（`failed_items: [{step, resource, error}]`），供管理员定位。
- 删除文件元数据（`file_artifacts` 记录）不等于删除物理文件——物理删除通过 `ArtifactStorage` 显式执行。

## 6. 安全要点

- 审计元数据不得保存密码、认证 Cookie、模型密钥、仓库凭证、完整源码或完整报告正文。
- 审计脱敏器递归处理所有嵌套结构，不只处理顶层字段。
- 项目删除后审计通过 `SET NULL` 保留最小脱敏上下文，不暴露已删除项目的敏感内容。
- 清理失败的物理文件路径在日志中脱敏（只记录逻辑键，不记录宿主机绝对路径）。
- 定时清理任务需要审计日志记录（清理范围、清理行数、失败项）。

## 7. 测试要点

### 7.1 审计模块

- 审计记录写入：关键操作触发审计、`result_status` 正确
- 脱敏器：密码/Token/Cookie 从 `metadata` 中移除；递归过滤嵌套敏感键
- `SET NULL` 行为：删除用户/项目后审计记录保留
- 审计写入失败时写操作的行为（不应静默成功）

### 7.2 清理模块

- 项目删除完整流程：容器销毁 → 文件清理 → 数据库级联
- 幂等重试：同一 `idempotency_key` 第二次执行时跳过已成功步骤
- 部分文件清理失败：项目行保留、失败项记录可诊断
- 运行中项目拒绝删除
- 容器销毁失败后的处理
- 定时保留清理：过期日志和资源按配置天数删除、`NULL` 时不清理
- 文件物理删除与元数据删除的一致性

### 7.3 数据库集成测试

- 删除项目 → 外键级联生效（所有子表记录消失）
- `audit_logs.project_id` → SET NULL
- `audit_logs.actor_user_id` → SET NULL
- 删除用户时 RESTRICT 阻止（如用户还有项目）
