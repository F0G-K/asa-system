# 调度与 AI 角色模块（scheduler + agents）

## 1. 模块概述

### 1.1 定位

`scheduler` 模块负责评估执行的阶段状态机推进、角色任务分发、并发控制和停止/失败收敛。`agents` 模块负责六类 AI 执行角色的定义、上下文组装、工具权限控制和模型调用适配。

两个模块紧密协作：`scheduler` 决定何时创建何种角色任务，`agents` 负责角色任务的具体执行。

### 1.2 设计依据

- `docs/1_PRD/自动化安全评估系统-PRD.md`
- `docs/3_概要设计/自动化安全评估系统-概要设计总纲.md` — 第 5.2 节、第 5.3 节、第 7.2-7.3 节、第 8.3-8.6 节
- `docs/4_开发规范/API接口文档.md` — 第 6 章（过程监控接口）
- `docs/4_开发规范/后端/后端开发规范.md` — 第 9 章（领域模型与状态机）、第 11 章（异步任务与调度）、第 12 章（AI 角色与模型调用）
- `docs/4_开发规范/数据库/数据库设计.md` — `runtime_stages`、`worker_tasks` 表设计

### 1.3 职责边界

**scheduler 职责：**

| 职责 | 说明 |
| --- | --- |
| 阶段状态机 | 管理 5 个固定阶段的 `idle → running → success/failed` 迁移 |
| 阶段串行推进 | 前一阶段 `success` 后启动下一阶段 |
| 角色任务分发 | 在阶段内创建 `worker_tasks` 记录并投递 Celery 任务 |
| 并发控制 | 阶段内仅对无依赖角色任务进行受控并行 |
| 停止收敛 | 检查 `stop_requested_at`，取消未开始的任务和阶段 |
| 失败收敛 | 关键角色失败 → 当前阶段 `failed` → 项目 `failed` |
| 恢复扫描 | Worker 启动时扫描异常停留的 `running` 任务 |

**agents 职责：**

| 职责 | 说明 |
| --- | --- |
| 角色定义 | 六类固定角色：`general`、`environment_inspector`、`code_analyst`、`vulnerability_verifier`、`report_editor`、`operations_assistant` |
| 上下文组装 | 按项目、阶段和角色最小化裁剪上下文 |
| 工具权限 | 每个角色仅能使用所属阶段允许的工具集合 |
| 模型调用 | 通过统一模型适配层调用 LLM，处理超时、重试、token 统计 |
| 输出校验 | 模型输出通过 Pydantic Schema 校验后再进入领域逻辑 |
| RAG 知识检索 | 在上下文组装时为 `code_analyst` 和 `vulnerability_verifier` 自动触发安全知识检索，增强分析准确率 |

**不负责：** 容器创建（runtimes）、源码拉取（projects/runtimes）、报告文件生成（reports）、WebSocket 推送（monitoring）——这些由对应模块处理。

## 3. 阶段调度模型

### 3.1 阶段定义

```text
固定顺序，严格串行：

  Stage 1: environment_scan     (环境扫描)
       ↓
  Stage 2: code_analysis         (代码分析)
       ↓
  Stage 3: vulnerability_verify  (漏洞验证)
       ↓
  Stage 4: report_generate       (报告生成)
       ↓
  Stage 5: done                  (完成)
```

### 3.2 阶段状态机

```text
idle → running → success
              ↘ failed
```

- 只有前一阶段为 `success` 才启动下一阶段。
- 阶段内关键角色失败后，当前阶段 → `failed`，项目 → `failed`。
- 取消检查：在阶段切换点检查 `stop_requested_at`，已标记停止则不再创建新阶段任务。

### 3.3 阶段状态实体

```text
RuntimeStage
├── id: UUID
├── project_id: UUID
├── runtime_id: UUID
├── stage_name: "environment_scan" | "code_analysis" | ...
├── stage_order: 1 | 2 | 3 | 4 | 5
├── stage_status: "idle" | "running" | "success" | "failed"
├── started_at: datetime?
├── finished_at: datetime?
├── error_message: str?
├── created_at: datetime
└── updated_at: datetime
```

数据库约束：
- `(runtime_id, stage_name)` UNIQUE — 同名阶段唯一
- `(runtime_id, stage_order)` UNIQUE — 顺序唯一
- CHECK 约束保证 `stage_name` 和 `stage_order` 对应关系

### 3.4 阶段推进流程

```text
启动项目时：
  事务内创建 5 条 runtime_stages (status='idle')

阶段推进：
  Worker 领取任务
    ├── 检查当前阶段前置条件（前一阶段 status='success'）
    ├── 更新当前阶段 status='running', started_at=now
    ├── 分发阶段内角色任务（创建 worker_tasks）
    ├── 发送 Outbox 事件 (stage_status)
    ├── 等待阶段内角色任务完成
    │     ├── 全部关键任务 success → 当前阶段 status='success', finished_at=now
    │     └── 关键任务 failed → 当前阶段 status='failed', error_message=...
    ├── 发送 Outbox 事件 (stage_status)
    └── 如果 success 且 stage_order < 5 → 投递下一阶段任务
       如果 stage_order = 5 → 项目 status='completed'
```

## 4. 角色任务模型

### 4.1 任务实体

```text
WorkerTask
├── id: UUID
├── project_id: UUID
├── stage_id: UUID
├── worker_role: WorkerRole       # 六类角色
├── task_content: str             # 任务描述
├── task_status: "idle" | "running" | "success" | "failed"
├── result_summary: str?          # 结果摘要（脱敏）
├── error_message: str?           # 错误摘要（脱敏）
├── request_id: UUID              # 全链路标识
├── idempotency_key: str?         # 幂等键
├── attempt_count: int            # 尝试次数
├── started_at: datetime?
├── finished_at: datetime?
├── created_at: datetime
└── updated_at: datetime
```

数据库约束：
- `(project_id, idempotency_key)` UNIQUE（项目内部分唯一索引）
- 复合外键 `(stage_id, project_id)` 强制任务与阶段同项目

### 4.2 任务状态机

```text
idle → running → success
              ↘ failed
```

- 用户停止项目不增加任务状态 `stopped`，取消原因写入 `result_summary` 或 `error_message`。
- 任务 `failed` 后根据角色重要性和阶段策略决定是否导致阶段失败。

## 5. 六类 AI 执行角色

### 5.1 角色定义

| 角色标识 | 所属阶段 | 主要职责 | 输出 |
| --- | --- | --- | --- |
| `general` | 全阶段 | 任务解析、上下文摘要、角色协作消息 | 任务分配、进度摘要 |
| `environment_inspector` | `environment_scan` | 技术栈识别、依赖分析、目录结构探索 | 技术栈报告、运行条件 |
| `code_analyst` | `code_analysis` | 源码安全分析、候选漏洞识别 | 候选漏洞、源码位置、初始证据 |
| `vulnerability_verifier` | `vulnerability_verify` | 漏洞可达性验证、触发条件确认 | 验证结论、复现步骤、验证代码 |
| `report_editor` | `report_generate` | 漏洞汇总、攻击路径整理、报告撰写 | Markdown 报告 |
| `operations_assistant` | environment_scan + 全阶段 | 容器操作、受控命令、文件处理、资源采样 | 命令结果、资源数据 |

### 5.2 角色工具权限

每个角色只能使用分配给该角色和阶段的工具集合：

| 工具 | general | env_inspector | code_analyst | vuln_verifier | report_editor | ops_assistant |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| 文件读取（只读源码目录） | — | ✓ | ✓ | ✓ | ✓ | ✓ |
| 目录遍历 | — | ✓ | ✓ | ✓ | — | ✓ |
| 关键字搜索 | — | ✓ | ✓ | ✓ | — | ✓ |
| 受控命令执行 | — | — | — | ✓ | — | ✓ |
| 漏洞数据库查询 | — | — | ✓ | ✓ | — | — |
| 依赖分析 | — | ✓ | — | — | — | — |
| 安全知识库检索（RAG） | — | — | ✓ | ✓ | — | — |

**绝对禁止：**
- 直接操作数据库（所有角色）
- 直接操作 Redis（所有角色）
- 直接访问 Docker Socket（所有角色）
- 访问宿主机路径（所有角色）
- 主动发起外网请求（除阶段策略允许的依赖下载）

### 5.3 上下文组装规则

```text
ContextAssembler
  │
  ├── 1. 项目元信息（名称、任务说明、环境类型）
  ├── 2. 前序阶段的结构化结果（技术栈报告、候选漏洞列表等）
  ├── 3. 当前阶段相关的源码片段（按文件路径和行号筛选）
  ├── 4. RAG 知识检索（仅 code_analyst 和 vuln_verifier）：
  │      ├── 从当前源码片段和项目技术栈提取检索要素
  │      ├── 调用 Embedding 模型生成查询向量
  │      ├── 在 pgvector 中执行 ANN 检索（按语言、子库过滤）
  │      ├── 重排序后截断到配置的 top-k
  │      └── 注入检索结果到上下文窗口
  ├── 5. 角色可用的工具列表和说明（含 search_security_knowledge）
  ├── 6. 输出 Schema 要求和示例
  └── 裁剪规则：
       ├── 上下文总 token 上限由配置控制（RAG 结果先于源码片段受裁剪）
       ├── 文件内容、搜索结果、检索结果按字符数截断
       └── 过滤凭证、密钥、环境变量和无关源码
```

## 6. 模型适配层

### 6.1 统一接口

```text
ModelPort (application/ports/)
  │
  ├── complete(prompt, context, tools, output_schema) → ModelResult
  ├── estimate_tokens(text) → int
  └── health_check() → bool
```

业务代码只依赖 `ModelPort`，不直接调用供应商 SDK。

### 6.2 适配层职责

| 职责 | 实现 |
| --- | --- |
| 供应商路由 | 按模型标识选择对应的 SDK |
| 超时控制 | 请求级超时 + 流式 token 间超时 |
| 限流处理 | 识别 429 响应，等待 `Retry-After` 后重试 |
| 重试策略 | 可恢复错误（限流、临时网络）指数退避 + 随机抖动 |
| Token 统计 | 记录 prompt_tokens、completion_tokens |
| 错误映射 | 供应商错误 → 统一 `ModelError` 子类 |
| 输出校验 | 响应先通过 Pydantic Schema，失败时有限重试 |

### 6.3 不可重试错误

- 参数非法、权限拒绝
- 模型输出结构持续非法（超过最大重试次数）
- 确定性业务失败

### 6.4 LangGraph 适配

LangGraph 只负责**单次阶段内**的角色执行图，不直接更新项目最终状态或推进跨阶段状态机：

```text
阶段内执行图（以 code_analysis 为例）：
  [code_analyst: 扫描入口]
        │
        ├── [code_analyst: 支付模块]
        ├── [code_analyst: 订单模块]
        └── [code_analyst: 数据库层]
        │
        └── [general: 汇总去重]
```

阶段内角色节点之间的消息和结果通过 `chat_messages` 记录，供前端回放。

## 7. RAG 知识检索

### 7.1 检索触发时机

RAG 知识检索在以下三个时机自动或按需触发：

| 触发类型 | 时机 | 检索范围 | 标识 |
| --- | --- | --- | --- |
| `stage_pre` | 阶段启动时，在所有角色任务之前 | 项目的技术栈、语言、框架级别的全局检索 | 全局安全背景注入 System Prompt |
| `role_pre` | 单个角色任务启动时，在上下文组装阶段 | 针对当前任务的源码片段、函数调用和候选漏洞的精准检索 | 角色任务级上下文增强 |
| `tool_triggered` | 角色在分析过程中主动调用 `search_security_knowledge` 工具 | 由角色按需指定查询意图 | 补充检索，受单任务调用次数限制 |

### 7.2 检索流程

```text
RAGRetriever.retrieve(context, role, stage)
  │
  ├── 1. 查询要素提取
  │      QueryExtractor.extract(context)
  │        ├── 编程语言与技术栈（来自 environment_scan 结果）
  │        ├── 关键函数调用（eval、system、exec、file_get_contents 等）
  │        ├── 文件路径模式（controller/、auth/、admin/ 暗示功能域）
  │        ├── 变量名与注释安全关键词（password、token、secret、bypass）
  │        └── 候选漏洞类型（来自 code_analyst 的前序输出）
  │
  ├── 2. 查询向量化
  │      EmbeddingPort.embed_query(extracted_query_text)
  │        → 1536 维向量（维度由 Embedding 模型决定）
  │
  ├── 3. 向量检索（pgvector）
  │      SELECT id, title, content_text, knowledge_type, risk_level,
  │             1 - (embedding <=> $query_vector) AS similarity
  │      FROM knowledge_entries
  │      WHERE entry_status = 'active'
  │        AND (language IS NULL OR language LIKE '%' || $lang || '%')
  │        AND knowledge_type = ANY($allowed_types)
  │      ORDER BY embedding <=> $query_vector
  │      LIMIT $top_k
  │
  ├── 4. 重排序
  │      Reranker.rerank(results, context)
  │        ├── 向量相似度（权重 0.6）
  │        ├── 语言/框架精确匹配加分（权重 0.2）
  │        └── 风险等级与当前分析上下文匹配加分（权重 0.2）
  │
  ├── 5. 上下文注入
  │      将重排序后的 top-k 条目按固定模板注入角色上下文
  │      每个条目包含：标题、内容摘要、来源子库、相似度分数
  │
  └── 6. 持久化检索记录
         INSERT INTO knowledge_retrievals (...)
```

### 7.3 检索配置

| 配置项 | 环境变量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 检索 top-k | `ASA_RAG_TOP_K` | 8 | 单次检索召回数 |
| 相似度阈值 | `ASA_RAG_MIN_SIMILARITY` | 0.65 | 低于此值的条目被过滤 |
| 单任务最大工具调用次数 | `ASA_RAG_MAX_TOOL_CALLS` | 5 | 防止角色过度依赖检索 |
| 检索结果最大 token | `ASA_RAG_MAX_RESULT_TOKENS` | 2000 | 注入上下文前的截断上限 |
| 子库权重 | `ASA_RAG_TYPE_WEIGHTS` | 见说明 | 四个子库的排序权重 |

子库默认权重：`vulnerability_pattern=1.0, security_standard=0.8, remediation_advice=0.9, historical_assessment=0.6`。历史评估库权重较低，因为跨项目结论可能不直接适用。

### 7.4 检索降级与容错

RAG 是增强而非必需——检索失败时角色在无知识增强的情况下继续分析：

```text
检索异常处理：
  ├── Embedding 模型不可用 → 跳过检索，角色正常执行，记录 warning 日志
  ├── pgvector 查询超时 → 降级为标签/关键词匹配（LIKE/ILIKE），记录 degradation 日志
  ├── 检索结果为空 → 返回空列表，不注入额外上下文
  ├── 向量维度不匹配 → 启动时 Fatal Error，阻止 Worker 启动
  └── 检索记录写入失败 → 记录 error 日志，不影响角色执行
```

### 7.5 安全约束

- 角色通过 `search_security_knowledge` 工具只能进行语义检索，不能执行任意 SQL 或向量查询。
- 检索查询文本在进入 Embedding 模型前脱敏（移除完整源码片段、IP 地址、密钥模式）。
- 检索过滤条件（语言、子库类型）由 Worker 端根据任务上下文自动附加，角色不能绕过。
- `knowledge_retrievals.query_text` 写入数据库前脱敏。
- 知识条目通过 `entry_status` 控制可见性，禁用条目不参与检索但保留数据。

## 8. 并发、重试与恢复

### 8.1 并发策略

| 层级 | 策略 | 实现 |
| --- | --- | --- |
| 项目间 | 全局并发上限 | `COUNT(*) WHERE project_status='running'` |
| 阶段间 | 严格串行 | 前一阶段 `success` 后才创建下一阶段任务 |
| 阶段内 | 受控并行 | 仅对无依赖角色任务并行分发 |
| 工具调用 | 串行/并行取决于角色策略 | LangGraph 节点定义 |

### 8.2 任务重试

```text
可重试错误：
  ├── 短暂数据库死锁 (deadlock detected)
  ├── 临时网络失败 (ConnectionError, Timeout)
  ├── Redis/Executor 短暂不可用
  └── 模型限流 (429) 和可恢复供应商错误

不可重试错误：
  ├── 参数非法、权限拒绝
  ├── 命令策略拒绝
  ├── 状态冲突
  ├── 模型输出结构持续非法
  └── 确定性业务失败

重试参数：
  ├── 有限次数（由配置控制）
  ├── 指数退避（base=2s, max=300s）
  ├── 随机抖动（±25%）
  └── 每次更新 attempt_count
```

### 8.3 停止协同

```text
停止检查点（在以下位置调用 CancelChecker）：
  ├── 角色调用前
  ├── 工具循环每次迭代后
  ├── 阶段切换前
  └── 新任务创建前

检查逻辑：
  if project.stop_requested_at is not None:
      停止创建新任务
      当前任务保存已有输出 + 停止原因
      当前阶段收敛
      项目 → stopped

注意：
  - Celery 撤销消息不能作为唯一取消机制
  - Executor 先发 SIGTERM，宽限期后 SIGKILL
```

### 8.4 Worker 启动恢复

```text
Worker 启动时扫描：
  ├── 查找 project_status='running' 但无活跃 Worker 心跳的项目
  ├── 查找 task_status='running' 但超过心跳超时的任务
  ├── 结合容器状态判断：
  │     ├── 容器仍运行 → 任务可能仍在执行，进入诊断状态
  │     └── 容器已停止 → 任务标记为 failed，阶段收敛
  └── 不自动把不确定任务标记为 success
```

### 9.2 关键实现约束

- **Celery Task**消息只包含可序列化标识（`project_id`、`stage_id`、`worker_task_id`、`request_id`、`idempotency_key`、`schema_version`），禁止传递 ORM Model、密码、Cookie 和完整源码。
- **Task 边界**：只做反序列化 → 建立上下文 → 检查幂等/取消 → 调用应用服务 → 确认/重试/失败。不自行拼装 SQL 或推进多个阶段。
- **幂等**：Task 执行前检查 `worker_task_id` 和幂等键；已成功任务重复投递时直接返回已有结果。
- **状态更新**：使用条件更新 `UPDATE ... WHERE task_status='idle'` 或行锁，受影响行数不为 1 时返回冲突。
- **LangGraph 边界**：LangGraph 不得直接更新项目最终状态或推进跨阶段状态机。项目、阶段状态仍由调度领域服务在 PostgreSQL 事务中维护。
- **模型输出**必须通过 Pydantic Schema 校验，非法输出仅在明确可恢复时有限重试。
- **RAG 检索**作为增强能力，失败时角色继续执行不中断；检索结果必须持久化到 `knowledge_retrievals`。
- **Embedding 维度**在 Worker 启动时自动检测并校验与 `knowledge_entries.embedding` 字段维度一致，不匹配时 Fatal Error 阻止启动。
- **知识库查询工具**是角色唯一可调用的知识检索入口，角色不能绕过检索服务直接执行向量查询或 SQL。

## 10. 安全要点

- 角色只能使用分配给该角色和阶段的工具集合，不能直接操作数据库、宿主机路径、Redis 和 Docker Socket。
- 上下文进入模型前过滤凭证、Cookie、密钥、环境变量和无关源码。
- 模型自由文本不能直接变成 Shell 命令、路径或数据库更新——必须通过受控工具的结构化参数生成并校验。
- 漏洞风险、路径、行号和证据在写入前执行业务校验和项目范围校验。
- 任务结果摘要（`result_summary`）和错误消息（`error_message`）在持久化前脱敏。
- 模型调用日志只保存脱敏摘要、耗时、token 和错误类别，不保存完整源码和密钥。
- RAG 检索查询文本在进入 Embedding 模型和写入 `knowledge_retrievals` 前脱敏。
- 角色不能通过 `search_security_knowledge` 工具绕过 Worker 端过滤条件进行全库查询。
- 知识条目管理操作（新增、编辑、禁用、删除）仅限管理员通过配置接口执行。

## 11. 测试要点

### 11.1 单元测试

- 阶段状态机全部合法和非法迁移
- 阶段顺序：只有前一阶段 `success` 后才允许推进
- 任务状态机：`idle → running → success/failed`
- 关键角色失败导致阶段失败
- 停止标记检查：`stop_requested_at` 非空时拒绝创建新任务
- 并发控制：阶段内无依赖任务并行分发逻辑
- 角色工具权限矩阵：每个角色只能使用允许的工具
- 模型输出 Schema 校验和非法输出处理
- 可重试/不可重试错误分类
- RAG 检索触发时机：`stage_pre`、`role_pre` 和 `tool_triggered` 三种类型
- 查询要素提取：从源码片段正确提取语言、函数调用和路径模式
- 检索降级：Embedding 不可用/超时/返回空时的容错行为
- 检索工具权限：只有 `code_analyst` 和 `vuln_verifier` 可调用
- 上下文注入格式：检索结果按固定模板注入且不超 token 预算
- Embedding 维度一致性校验：不匹配时 Worker 启动失败

### 11.2 Worker 集成测试

- Celery 任务重复投递（幂等）
- 任务有限重试和达到上限后收敛为失败
- 取消信号检查：任务在角色调用前后和工具循环中响应取消
- Worker 重启恢复扫描：`running` 任务根据容器状态进入诊断流程
- AI 适配使用 Fake 模型（不调用真实收费服务）

### 11.3 API 测试

- `GET /api/v1/projects/{project_id}/stages` — 5 个阶段按顺序返回、阶段状态更新反映
- `GET /api/v1/projects/{project_id}/workers` — 分页、按阶段/角色/状态筛选、敏感信息脱敏

## 12. 配置项

| 配置项 | 环境变量 | 说明 |
| --- | --- | --- |
| 最大并发项目数 | 来自 `system_configs.max_concurrent_projects` | 运行时读取生效配置 |
| 任务最大重试次数 | `ASA_TASK_MAX_RETRIES` | 默认由容量测试确定 |
| 任务重试退避基数 | `ASA_TASK_RETRY_BACKOFF_BASE` | 默认 2s |
| 任务心跳超时 | `ASA_TASK_HEARTBEAT_TIMEOUT_SECONDS` | Worker 启动恢复用 |
| 模型请求超时 | `ASA_MODEL_REQUEST_TIMEOUT_SECONDS` | 默认由容量测试确定 |
| 模型最大输出 token | `ASA_MODEL_MAX_OUTPUT_TOKENS` | 按角色和阶段可差异化 |
| 上下文最大 token | `ASA_CONTEXT_MAX_TOKENS` | 进入模型前的裁剪上限 |
| RAG 检索 top-k | `ASA_RAG_TOP_K` | 默认 8 |
| RAG 最小相似度阈值 | `ASA_RAG_MIN_SIMILARITY` | 默认 0.65 |
| RAG 单任务最大工具调用 | `ASA_RAG_MAX_TOOL_CALLS` | 默认 5 |
| RAG 检索结果最大 token | `ASA_RAG_MAX_RESULT_TOKENS` | 默认 2000 |
| Embedding 模型名称 | `ASA_EMBEDDING_MODEL` | 默认由供应商确定 |
| Embedding 请求超时 | `ASA_EMBEDDING_TIMEOUT_SECONDS` | 默认 10s |
| pgvector 索引探测数 | `ASA_PGVECTOR_PROBES` | 默认 IVFFlat probe = 10 |

未确认的配置项不得在代码中写死默认生产值。
